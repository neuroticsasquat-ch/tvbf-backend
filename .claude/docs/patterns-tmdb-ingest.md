# TMDB ingest, delta, tombstoning and popularity

> Extracted from `.claude/CLAUDE.md` (2026-08-19) to keep the always-loaded file under the context limit.
> Read before touching `tmdb/{client,ingest,update,tombstone,export,popularity}.py`, `POST /admin/catalog-ingest`, `POST /admin/catalog-update` or the scheduled `tvbf.jobs.catalog_update`.

These are load-bearing and easy to get wrong.

**TMDB auth is a bearer header, and the `append_to_response` cap is 20 — measured.** The credential is the TMDB account's *API Read Access Token* (the long JWT), sent as `Authorization: Bearer`, never the v3 `api_key` query parameter — a key in a query string is copied into access logs, proxy logs and any error report that echoes a URL, none of which can revoke it. TMDB's docs call the bearer style "v4 auth"; that is a naming quirk, not an endpoint version, and it authenticates the v3 endpoints (`api.themoviedb.org/3`) this app calls. Real value goes in the gitignored `.env` (compose interpolates it in); `.env.example` is committed and carries a blank placeholder. `scripts/probe_tmdb_append_limit.py` measured the append cap against the live API on 2026-08-09: **20 entries come back in full** (every appended `season/N` carries its complete episode list), **21 is a hard HTTP 400** — TMDB fails loudly rather than truncating. Namespaces and `season/N` entries share those 20, so every namespace costs a season; use `plan_append()` rather than slicing by hand, and fetch the overflow with `get_tv_season()`. `DEFAULT_APPEND` is the audit's **11 namespaces plus NEU-1052's `recommendations`** — **12**, leaving eight season slots. The twelfth was exactly the decision about the season budget this line warns a twelfth is: measured across all 210,343 mirrored shows carrying ingested seasons, 96.84% fit inside seasons 0–8 against 96.34% inside 0–7, so it costs 1,054 shows one extra `get_tv_season` each (~2.5 min on a full pass) against a surface that would otherwise need a multi-hour backfill every time it went stale. A thirteenth is the same decision again, not a free addition. The client leases **25** tokens per locked budget transaction (TV Maze leases 1) — at 20 req/s a lock per request is 20× the pressure ADR-0006 was validated at.

**The catalog ingest's work list is `tmdb_synced_at IS NULL`, and "row already present" would be wrong.** The retired `tvmaze/ingest.py` resumed by diffing the feed against rows that exist, which was safe there because only that ingest created them. In `catalog` it is not: NEU-1042 copied ~89k TV Maze shows in and NEU-1043 mapped a `tmdb_id` onto ~63k of them, so those rows exist and are correctly identified while still holding **TV Maze data**. An ingest resuming on row-existence would skip precisely the shows users track and finalise the run as a success. `catalog.show.tmdb_synced_at` (NEU-1034) is therefore set only once a *complete* payload has been mirrored — the same device `tvmaze.show.akas_synced_at` already is — and `mark_series_synced` stays out of `upsert_series_payload` because that function also writes the narrower payloads a delta produces, which cannot claim a full pass. The corollary: **an overflow season that fails takes the whole show down with it**, since a show written with one season missing and then stamped would be retired from every future work list.

**The first request guesses seasons 0–8, and both halves of that guess are measured.** A show's season numbers are only knowable from a response not yet made, but `append_to_response` has to be built before the request goes out — so `tmdb/ingest.py` speculates and then reconciles against `seasons[]`, fetching the rest with `get_tv_season`. `scripts/probe_tmdb_season_speculation.py` measured both unknowns against the live API on 2026-08-10: **guessing is free** (a `season/N` a show does not have is dropped from the response silently, 200 OK — had TMDB 400'd, speculation would break the ingest for the single-season series that are most of the catalog), and **0..8 beats 1..9** (97.5% of 200 sampled series have every season inside it, against 94.0%; specials are rarer than expected at 3.5%, ninth numbered seasons rarer still). `SPECULATIVE_SEASONS` is derived from `APPEND_TO_RESPONSE_LIMIT - len(DEFAULT_APPEND)` so a twelfth namespace narrows the window rather than overflowing the cap into a hard 400. Correctness never rests on the guess — the reconcile covers whatever it missed; the guess only decides how many shows cost two requests.

**The catalog ingest writes no `last_update_cursor`, and its run rows live in `catalog.ingest_run`.** No cursor because TMDB's delta is a date range rather than a per-show epoch (NEU-1035), so there is nothing to hand forward and a value in that column is one the next reader misreads. The table sat in `tvmaze` until NEU-1051 because run rows are operational metadata rather than catalog data, and a second copy would have meant a second stale-run cleanup, a second liveness guard and a second status route while both spines stood; it moved with `ALTER TABLE ... SET SCHEMA`, so every historical row came with it. The kinds are `catalog_initial` and `catalog_update`, each added to `ck_ingest_run_kind` NOT VALID.

**The catalog delta's cursor is a date, and its lineage is what makes that safe.** `/tv/changes` takes a date *range* (14-day maximum, 100 per page, `id` + `adult` only), so `last_update_cursor` holds the end of the last window covered — stored as the epoch of its midnight UTC, read only through `CATALOG_CURSOR_KINDS`. `get_last_successful_cursor` has always been scoped by lineage precisely so one axis cannot resume from another's watermark; that scoping is the only reason a date may share a column with TV Maze's epochs, and it is why `tmdb/ingest.py` still writes nothing there at all. Five consequences, each easy to undo: **windows share their boundary day** (both bounds are inclusive upstream, so disjoint windows drop every change dated on the seam — the duplicate is deduplicated before any show is fetched); **a window past TMDB's 500-page cap is halved and retried, never truncated** (50,000 changed series is out of reach for a day and in reach for a 14-day window, and truncating would drop the overflow *and* advance the cursor past those days; a single day over the cap raises, because there is nothing left to halve); **the cursor advances only on a run that finished**, so an aborted run re-covers its whole gap — a *per-show* failure below the abort threshold is stepped over on purpose, since rewinding to retry one show would let a permanently-broken series widen the gap nightly; **the first delta bootstraps off the full pass's earliest attempt's `started_at`**, not its successful run's and not its `finished_at`, because that pass is resumable and runs ~8.7h, so a show mirrored by attempt one was stamped days before the last attempt began; and **a changed id says nothing about what changed**, so every hit is a full re-fetch through the same `mirror_series` the full pass uses.

**Tombstoning rides on the delta, and is best-effort there.** `/tv/changes` cannot report a deletion, so ADR-0005's reverse diff runs against the *full* daily export instead (NEU-1036, ADR-0009) — downloaded at the end of a delta that completed, because the export costs no rate budget and no credential, and daily is the cadence ADR-0005 already established. Four things it does that the TV Maze version does not, each load-bearing: it **diffs on `tmdb_id`, not the primary key** (`catalog.show.id` is a surrogate the migration seeded from TV Maze's ids, and means nothing to the export); it **excludes `tmdb_id IS NULL` rows** from both the diff and the plausibility count, because a locally-authored row was never in the export and flagging it would defeat the mechanism protecting user data; its **floors are recalibrated against 228,611** — `_MIN_FEED_ABSOLUTE` 150,000, and the 95% relative floor measured against `max(mirror, 228_611)` rather than against the mirror alone, because the mirror is ~63k rows until cutover and 95% of that would wave through an export missing a third of TMDB — and when either trips nothing is written *including resurrections*; and a **failed export download is caught and logged, never fatal** — failing the run would hold the cursor back and re-cover the whole window nightly, the widening gap NEU-1006 exists to avoid, in exchange for a reconciliation that can simply happen tomorrow. A truncated download is caught before it reaches the diff: `export.py` checks the body against `Content-Length` and decompresses the gzip member whole, so a short file raises `TruncatedExportError` rather than passing for a small catalog. Since NEU-1172 the download is **shared with the popularity refresh** and happens once, ahead of both — so a failed download is logged as such rather than as a tombstone failure, and the two passes are guarded separately so a database failure in one does not cost the other its night.

**The popularity refresh rides the same export, and writes one column.** `/tv/changes` reports *content edits* and TMDB recomputing a score is not one, so without this pass `catalog.show.popularity` freezes for the 97% of the catalog a delta never re-fetches (measured 2026-08-16: 200,698 of 229,443 rows last synced 2026-08-10, against 1,300–2,300 re-synced a night). `tmdb/popularity.py` (NEU-1172) reads the `popularity` every export line already carries and costs **no request, no rate budget and no credential**. Six things are load-bearing. It **writes `popularity` and nothing else** — the export's `original_name` is not `catalog.show.name` and is no substitute for one, and this is not an ingest. It **touches neither `tmdb_synced_at` nor `credits_synced_at`**: a score arriving from the export is not evidence a payload was mirrored, and stamping either would retire a show from a work list it belongs on — the distinction NEU-1127 had to draw when it added the second watermark rather than reuse the first. It **matches on `tmdb_id`**, like every other `catalog` write. It **consults the same floors as the tombstone pass** on the same file, so a partial download cannot skew scores here while writing no tombstones there. A **line whose popularity will not parse keeps its id and loses only the score** — dropping the whole line would read as absence to the tombstone diff and tombstone a series over a malformed float — and its row is left alone rather than nulled, as is any show absent from the export (that is the tombstone pass's question). And the write is a batched `UPDATE ... FROM (VALUES …)` carrying **`IS DISTINCT FROM`**, which is what makes a re-run genuinely free rather than merely idempotent: without it every nightly pass rewrites all 229k rows and their dead tuples whether or not a score moved.
