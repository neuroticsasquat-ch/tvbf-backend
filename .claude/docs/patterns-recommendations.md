# LLM client and the weekly recommendations pipeline

> Extracted from `.claude/CLAUDE.md` (2026-08-19) to keep the always-loaded file under the context limit.
> Read before touching `src/tvbf/llm/`, `src/tvbf/recommendations/`, `jobs/weekly_recommendations.py`, `RECOMMENDATION_MODEL`, `PROMPT_VERSION`, or `GET /me/recommendations`.

These are load-bearing and easy to get wrong.

**`src/tvbf/llm/` is a deliberate copy of `upcoming-movies-backend/src/upmovies/llm/`, and the drift is accepted in writing.** NEU-1098 ported the provider-neutral prompt type, the OpenAI-compatible client and the retry policy; it left `pricing.py`, `offline.py`, the Anthropic adapter, the four-stage configuration validation, the `CallLog`/`CallResult` telemetry and the byte-identical-prefix caching contract, all of which are earned by upmovies' four stages across three providers and inert for one stage calling one provider a few times a week. A shared package is the textbook answer and the wrong one here — two personal repos, no shared publishing setup, and it would couple TVBF's release cadence to upmovies'; if a third consumer appears, *that* is when extraction pays. Each module's docstring records what it took and what it left, and a fix in one repo does not reach the other. Five things are load-bearing. **The instruction must contain the literal lower-case word "json"**, measured by upmovies against the live endpoint: DeepSeek answers 400 when `response_format` is set and the word appears nowhere, which is non-retryable, so `client._to_wire` *enforces* it rather than trusting a comment — nobody "cleaning up" the wording can get past it. The match is **case-sensitive** and reads **`system` only**, both stricter than the provider and both deliberate. **NEU-1100 re-measured all three against DeepInfra on 2026-08-15 and none of them reproduced** — see the next paragraph, which supersedes the reasoning this sentence used to carry ("nobody measured whether upstream lowercases before looking"). Somebody has now: they do not enforce it there. The enforcement stays regardless, on the cost asymmetry rather than on the provider's behaviour — a false refusal is loud, local and one word to fix, and the 400 it stands in front of costs a user their week — and the word still belongs with the authored instruction rather than incidentally inside a payload that varies per call. **The exception taxonomy is what M4's failure semantics are written against**: `LLMResponseInvalid` is retried once by the job, `LLMRequestFailed` never is (the client already walked the backoff curve), and `UnsupportedPromptError` sits outside `LLMError` as a `ValueError`, because nothing was sent and there is no call outcome to classify. Two things keep that airtight and both look like tidiness until they are not: the envelope is read through `api_payloads.ChatCompletion`, because a `payload.get("choices")` chain over a body that decoded to a list raises `AttributeError` — neither subclass, so a job dispatching on `LLMError` misses it; and `_post` translates a limiter failure into `LLMRequestFailed`, because `DatabaseRateLimiter` **fails closed** and NEU-1099 points this at the shared row, so a database blip arrives as a `SQLAlchemyError` that would escape the same way. **`input_tokens` is the provider's whole `prompt_tokens`**, deliberately diverging from upmovies, which subtracts cached tokens to keep four counts disjoint so `price()` cannot charge them twice — `pricing.py` is not ported, so there is nothing to double-charge and subtracting would understate the prompt actually sent. **The base URL is a registry constant and the model id is config**: a base URL is a property of the provider rather than of a deployment, and `RECOMMENDATION_MODEL` has no default on purpose — the exact DeepSeek id on DeepInfra is NEU-1100's to measure, and one asserted from memory is a non-retryable 404 that looks like an outage. And **the budget is shared by default and the rate arguments are required** (NEU-1099): `limiter=` is now the opt-out an isolated caller (every unit test) passes, while `rate_calls` / `rate_window` stay required even for those callers, so a construction site always states the budget it means instead of inheriting a default written once in the client — NEU-1098 shipped `limiter=` required precisely because required-then-optional is the only direction in which nothing ships silently un-budgeted, and this codebase has twice paid for a bare per-process limiter (NEU-955, then ADR-0006). `_budget` takes **no lease**, unlike TMDB's window's worth: leasing amortises lock traffic on a source hit tens of times a second, and this one is called once per changed user per week. The limiter is acquired *inside* the retried operation, because a retry is a request upstream sees.

**The DeepSeek model id, JSON mode and the account-scale latency are measured, and the "json" constraint did not reproduce.** `scripts/probe_deepinfra.py` (NEU-1100) settles all four against the live API; run it inside the container with `DEEPINFRA_API_KEY` set, and `--model` (repeatable) to measure specific ids at account scale. Everything below was measured 2026-08-15. **DeepInfra's catalog offers 185 models, nine of them DeepSeek, and all nine answer a real call** — the originating stub's `deepseek-ai/DeepSeek-V4-Flash` among them, so that guess was right *and* unverifiable, which is exactly why `RECOMMENDATION_MODEL` has no default in `config.py`. The value it settled on was `deepseek-ai/DeepSeek-V4-Pro-0813` — and **keeping the id out of code was the half of that decision which held up**, because production never actually ran it and NEU-1180 has since replaced it with the id Coolify holds on an axis this probe does not measure at all (see *the model is chosen on capacity* below). A default in code is a claim the client keeps making after an id is retired upstream **or outgrown**. **Since 2026-08-18 the id is not recorded in the repo at all** — not in `config.py` and no longer in `.env.example`, which now ships blank: `tvbf-backend` is a public repo, the running id is the output of an expensive two-stage screen, and the measurements behind it — **including the running id itself, which is deliberately named nowhere in this repo, this file included** — live in `<umbrella>/docs/recommendations-model-measurements.md`, which is outside version control. Production reads it from the Coolify UI. Everything still in the public repo names a **superseded or rejected** id, which is deliberate: those say what is *not* running. Five things are load-bearing.

**Latency has to be measured at account scale, because the trivial-prompt times do not rank the models — but latency is not what should choose the model.** On the 522-show payload `V4-Pro-0813` runs a **6.87s median** (6.24–7.07 over three runs) against `V4-Flash`'s **17.78s** (17.02–20.50), and an earlier session put Flash at 21.02s (16.47–23.90) — so roughly **2.5–3× slower**, session to session. On `"ok?"` the two sit within half a second of each other (0.33–0.37s against 0.63–0.82s) and an earlier run timed Flash at 0.30s. A catalog listing plus a smoke call tells you an id exists and whether it is a reasoning model; it does not tell you which id to set. Both returned 25 of 25 usable recommendations on every run — **on one synthetic payload, at one size, which is this measurement's blind spot**: compliance was never varied against library size, and that is precisely where the real failure turned out to live.

**A reasoning model cannot serve this client at all.** `DeepSeek-R1-0528` answers 200 with a `<think>…</think>` block ahead of its JSON on every one of the four JSON-mode requests, so the content never decodes and `client._parse_object` would raise `LLMResponseInvalid`; at account scale the call exceeds the client's production 60s ceiling and comes back `LLMRequestFailed` instead. Both measured directly (`--model deepseek-ai/DeepSeek-R1-0528 --runs 1 --timeout 60 --retries 0`). This is why the probe carries the **fastest smoke responder** rather than the catalog's first entry: the catalog is alphabetical and its head is R1, which cost the probe's own first session three runs of nothing but timeouts.

**`response_format: {"type": "json_object"}` is honoured, and none of the recorded 400 behaviour reproduced.** Four requests on each model — the word "json" lowercase in `system`, the word nowhere at all, uppercase `"JSON"` only, and the word in the `user` message only — every one answered **200**, with a decodable JSON object on both chat models and a think-block on R1. `client._to_wire`'s guard, its case-sensitivity and its `system`-only reading are therefore all **stricter than the provider measured on this date**, where NEU-1098 recorded them as *possibly* stricter. **The guard stays, and this paragraph is the argument for keeping it knowingly rather than for deleting it**: the evidence is three ids on one day out of a catalog of nine that rotates, the guard fails loudly and locally one word from fixed before anything is sent, and the failure it stands in front of is non-retryable and costs a user their week. Deleting it is a decision to trust that no id the setting can name enforces the rule.

**The payload costs more than §5.3 costed it, and the malformed-response retry is priced against a failure nobody has seen.** The 522-row account payload is 17,825 bytes of JSON and **6,748 input tokens** with the instruction — against the spec's ~4.7k estimate for the rows alone; output is ~1,000–1,200 tokens for 25 recommendations. Across **nine** account-scale calls spanning two chat models, every response parsed as a JSON object and yielded 25 of 25 usable recommendations, with none dropped for a missing `release_year`. So `types.LLMResponseInvalid`'s single retry is insurance against something with an observed rate of zero: keep it (one extra call a week costs a fraction of a cent) and do not build anything further on the assumption that malformed JSON is common here. **A failure with a non-zero rate turned up on 2026-08-17 and it is a different one**: a production run stored 5 of 25 because the model wrote its reasoning into `title` (`"The Americans' Russian counterpart, 'The Bureau'"`) while every entry stayed structurally valid, so the parse dropped nothing and this retry never fired. Nine clean account-scale calls said nothing about it, because compliance was never what they measured. The response was unusable and only *resolution* could tell — see the weekly pass's retry below, which is why that retry is no longer `LLMResponseInvalid` alone.

**The model is chosen on capacity at payload size, and that is a different axis from everything above.** NEU-1180: a production run on 2026-08-18 came back `no_matches` with 0 rows stored because all 25 returned titles were series the user already had, and §8's filter dropped every one. It fails **silently** — `GET /me/recommendations` serves the newest *succeeded* set, so the page keeps showing last week's list and the user's report is "nothing changed" rather than "it's broken". `scripts/probe_deepinfra_capacity.py` replayed the exact failed payload across 100 DeepInfra models, padded with real catalog titles to simulate growth, scoring *usable* — returned titles that are distinct **and** absent from the payload, which is self-scoring and needs no ground truth. Six things are load-bearing. **The id production ran, `deepseek-ai/DeepSeek-V4-Flash-0731`, scores 0 usable at 260 series** — the library we already have — against the chosen model's 25/25/24/20 at 260/500/1000/2000 for ~$0.04 per user per year; so this was never a scaling threshold to plan for, it was a model that could not do the job. **`RECOMMENDATION_MODEL` is set in the Coolify UI, never the compose fallback**, which Coolify seeds from once and then shadows, so a compose edit is a silent no-op in production. **The chosen model is deliberately not the best scorer**: `Seed-2.0-pro` has the better curve and gave the worse answers on a real payload (Dexter, Prison Break, The Big Bang Theory for a prestige-cable profile, where the chosen model gave Broadchurch, Happy Valley, Line of Duty), so **compliance screening cannot decide this alone** and any future change needs both stages — the automated curve, then a human reading one real payload's output. **No `PROMPT_VERSION` bump**, because the model id is already inside the payload hash, so every user regenerates on the next run by construction; the same property makes a model swap a regeneration event, not a silent drift. **Five other explanations were measured and refuted** before the model was blamed: a frequency/presence penalty does nothing (`scripts/probe_deepinfra_penalty.py`, median usable 2 → 1); capping the `liked` list trades non-compliance for blindness (~8 of 25 slots go to shows the capped payload no longer names); multi-round correction frequently returns 0 new; retrieve-then-rank from `catalog.show_recommendation` scores **recall@331 of 1-of-21** against a known-good week and would have replaced Chernobyl, Rectify, Patriot and Counterpart with Gotham and Tulsa King; and a markdown-fence parsing bug on our side is dead at 0 of 3 fenced across four models. And **both probe scripts are committed with their findings in their docstrings**, because DeepInfra's catalog rotates and the sweep is the thing you re-run rather than the thing you remember. **The sweep screens compliance and cannot screen latency, which is the sixth thing and the one it got wrong**: `probe_deepinfra_capacity.py` scores its calls at `timeout=240`, four times `retry.DEFAULT_RETRY_POLICY`'s, so a model can top the curve and still be unable to answer inside production's ceiling — the chosen model runs a **49.2s median / 57.0s max** on a 522-row payload against the 60s that ceiling then was, and on 2026-08-18 both real accounts were recorded `failed` with a null `raw_response` after four attempts apiece, 4m05s end to end. The timeout was raised to **150s** in response (see `llm/retry.py`), which is the decision to fit the ceiling to the model rather than the model to the ceiling; the standing rule either way is that **a model change is not finished until `scripts/probe_deepinfra.py --model <id>` has timed it at account scale**, because the curve alone will happily pick a model the client cannot wait for.

**The taste payload's row order is part of its hash, and its exclusion set is deliberately wider than its rows.** `recommendations/payload.py` (NEU-1104) is one object doing three jobs — the model's entire input, the regeneration gate's hash input, and the never-recommend list — and three things hold it up. **Rows sort by folded title, then year, then show id**, in Python over the fold Postgres returned with the titles (`show_repo.titles_for_ids`): without a *total* order a query-plan change reorders rows, every hash differs and every user regenerates for nothing, which is exactly the churn spec §9.1 exists to prevent — and the first two terms are not unique, so the show id is what makes "sorted" mean one arrangement. **The hash covers `prompt_version` and the model id**, newline-separated rather than concatenated so `("1", "a/b")` and `("1a", "/b")` cannot collide into a silent skip; `PROMPT_VERSION` lives in that module and must be bumped in the same commit as any change to the prompt text or the payload's shape, or a prompt change re-runs nobody — and since NEU-1173 it versions **the whole request/response contract, of which the reading side is half**: version 4 changed no instruction text at all, it added the recovery of a dressed title, which is the same payload and the same instruction producing different stored rows, exactly the condition the rule names. And **`excluded_show_ids` is a wider set than the tier rows** — it adds the shows the INTERESTED cap dropped, the shows no §5.1 tier covers, and the shows carrying only an episode rating, which is why the set comes from `recommendations/exclusion.py` rather than from the tiers: `taste_for_user` deliberately refuses to let an episode rating *enrol* a show, but "we have no opinion about this show" and "the user has never seen it" are different claims and only the second licenses a recommendation. **Since NEU-1175 that module is the one place the set is defined** — until then this module unioned the taste signals' keys with an `episode_rating_repo` call of its own, which was correct only because the taste universe happened to be three of the four sources then in it. NEU-1178 added a fifth, a **dismissal**, which is the one member that need not name a show the user has ever seen — so it lands in the `exclude` group like the rest and reaches no tier, `PROMPT_VERSION` moves to `"5"`, and `liked_count` / `interested_count` / `interested_before_cap` and the generation floor are all untouched, because `taste_for_user` never sees it. The floor (`(2 x liked) + interested >= 10`) counts the rows actually emitted, which the cap can never change — it caps at 50.

**Since `PROMPT_VERSION` 3 the payload also *names* every excluded show, in an `exclude` group, and that group is a bug fix rather than a nicety.** Under versions 1 and 2 the ban covered shows the payload never mentioned, so the model was asked to avoid rows it could not see — an instruction nothing could follow. On 2026-08-17 at 16:00 UTC a production run returned 25 clean bare titles of which **25 of 25** were already in its own input, stored none of them, and recorded `no_matches`; the run before it had stored 5 of 25 for the *title* reason (see `recommendations/prompt.py`, which holds both accounts). Four things: the group carries **`EXCLUDE_COLUMNS` — title and year only**, because an excluded show reached no tier and two nulls a row across a long tail is real tokens asserting nothing; it names only shows **no tier group already shows**, since a tier row is visible as itself, and `TastePayload.excluded_row_count` is that number rather than `len(excluded_show_ids)`; it sorts on `_rows`' key so the order is **total**, for the hash reason above; and `titles_for_ids` is now asked for the **union** of the tier ids and the exclusion set, one query rather than two. The instruction names all four groups the ban covers and — the half version 2 was missing — says what to do instead: drop the series without comment and give the next best one not yet used.

**Resolution is two fold-exact tiers and nothing after them, and the negative decisions are the design.** (Still two, and still nothing after them — the one repair that exists for a title `resolve` cannot match lives *above* it, in the weekly pass; see the dressed-title paragraph below.) `recommendations/resolution.py` (NEU-1107) turns a model-authored title plus year into a `catalog.show` id — fold-exact on `show.name`, then on `show_aka.title`, premiere year within ±1, `None` otherwise — and it is **entirely local**, so ADR-0002 holds without exception. Six things hold it up. **There is no fuzzy or trigram fallback**: a similarity threshold answers a human-search-box problem (typos) that does not exist here, since an LLM either knows a show or invented one, so it buys almost no true matches while turning every hallucination into a confident wrong match — the two trigram indexes it reads with `=` (`ix_show_name_folded_trgm`, `ix_show_aka_title_folded_trgm`) are not an invitation to start reading them with `%`. **Ambiguity resolves by `popularity DESC NULLS LAST`, not to unmatched**, which deliberately inverts NEU-1043: there a false positive attached a user's watch history to the wrong show and was unrecoverable, here it shows a less-likely card in a grid of twelve. **The tier order is not a popularity contest** — a name match beats a more popular AKA match, because tier 2 is only reached when tier 1 found nothing, which one merged query ordered by popularity would quietly undo. **A title that folds to nothing never matches** (`"!!!"` and `"???"` fold alike), the same guard `sql_fold.folded_equal` carries. **An undated show never resolves**, because the year is the only disambiguator there is. And **it decides nothing about who may see the show**: the never-recommend set is the taste payload and belongs to the caller, while `adult` / `deleted_upstream_at` are filtered at read time (§8) — a write-time copy here would be the weaker half of that filter and would make a resurrected show permanently unrecommendable.

**"The current set" is one query in one module, and the `succeeded` filter is what makes an unhappy run non-destructive.** `app/repos/recommendation_repo.py` (NEU-1108) is the newest `app.user_recommendation_set` per user carrying `status = 'succeeded'`, plus the companion that loads that set's rows joined to `catalog.show`. Both are built from one private scalar subquery, because the weekly pass reads this to compare payload hashes and `GET /me/recommendations` reads it to serve — and two implementations is how the pass decides a user is up to date while the surface shows something else. Three things are load-bearing. **A `failed` / `no_matches` / `insufficient_history` set is recorded, is newest, and is invisible to every reader**, which is what leaves last week's recommendations standing when the provider 503s at 4am rather than blanking the section (spec §9) — it is also why a set carrying a `payload_hash` at every status is safe for the gate to read *through this function* and not safe to read directly. **The ordering carries `id DESC` behind `generated_at DESC`**: that column defaults to `func.now()`, the *transaction* timestamp, so two sets written in one transaction tie exactly, and a `LIMIT 1` over a partial order lets Postgres hand the gate one row and the API the other. And **`adult` / `deleted_upstream_at` are filtered here, on the read**, because a set generated in March can name a show tombstoned in June — the 25-asked-for / 12-displayed headroom (§7) is what absorbs it, and the surface decides how many of what survives it shows.

**The model-response fixtures are recordings, and the malformed one is the reason.** `tests/fixtures/recommendations/` holds three real DeepInfra bodies, whole envelope and `usage` included, taken by `scripts/record_recommendation_responses.py` on 2026-08-15 (NEU-1107, project spec §12): `clean.json`, 25 recommendations that all resolve; `obscure.json`, 25 from an international profile where `Twin Peaks: The Return` resolves to nothing — a real catalog gap, since the mirror holds *Twin Peaks* (1990) and models the revival as a season of it — and four (`Trapped` → *Ófærð*, `Deadwind` → *Karppi*, `The Chalet` → *Le Chalet*, `Suburra: Blood on Rome` → *Suburra: La Serie*) resolve only through the AKA tier; and `malformed.json`, `DeepSeek-R1-0528` answering 200 with `finish_reason: "stop"` and a `<think>` block ahead of its JSON, so the content does not decode and the client raises `LLMResponseInvalid`. That last one is what a hand-written fixture would never have contained, which is the whole argument for recording rather than authoring them. Three rules: **25 and the model id are both load-bearing** — 25 is what §7 asks the pass for, and the id is the one the pass will actually call (NEU-1100's `deepseek-ai/DeepSeek-V4-Pro-0813` when these three were recorded; NEU-1180 replaced it, so the recordings now predate the running model and should be retaken the next time the §7 contract moves — and since 2026-08-18 the recorder has no id to inherit, so `--model` is now mandatory rather than merely advised), so pass `--model` rather than letting the recorder inherit a local `RECOMMENDATION_MODEL` that has drifted (a recording from a model the pass will not call pins the wrong shape, and nothing downstream notices); the recorder's instruction is **not** the weekly pass's prompt (NEU-1109 owns that), so re-record when the §7 output contract changes and not when wording does; and the claims about which titles resolve were checked against the **real local catalog** while the tests seed their own rows — otherwise a fixture shaped to agree with the test proves nothing.

**§10's sequential-versus-concurrent threshold survives the measurement, for a different reason than it was written.** At the measured median a sequential weekly pass is 0.6 min at 5 users, **11.4 min at 100 and 22.9 min at 200** — so the 100–200 range is a claim about how long an operator will tolerate one job running, not about anything breaking. The client's 60s per-attempt timeout is nowhere near binding for the model that latency was measured on, and is still ~3× the slowest Flash run; the only id measured to breach it is the reasoning one. **NEU-1180 then made the timeout binding for the first time, and re-costed the arithmetic.** The chosen model was screened on capacity and *not* timed, which is how a model with a 49.2s median reached production against a 60s ceiling; measured after the fact it puts a sequential pass at **4.1 min at 5 users, 82 min at 100 and 164 min at 200** — seven times the figures above, so §10's 100–200 range is now a claim about tolerating something closer to an hour and a half. The timeout is 150s to fit it. If that range starts to bite, the fix named at the weekly pass — a bounded semaphore, never a second process, which the advisory lock refuses by design — is what buys it back, and it bounds the *failure* path first: at `max_retries=3` a wholly dead user costs `4 x 150s`, and sequentially those stack.

**The weekly pass's guard is an advisory lock, and a below-floor user is written every week.** `jobs/weekly_recommendations.py` (NEU-1109) takes `pg_try_advisory_lock(ADVISORY_LOCK_KEY)` on **its own connection**, held for the whole pass — a session-level advisory lock belongs to a *connection*, so taking it on a pooled session that later commits hands its lifetime to the pool rather than to the job. The key is a fixed `int64` constant and must stay one: a value derived from anything is a way for two deployments to disagree silently, and Postgres advisory locks share one keyspace per database, so a second job wanting one picks a different constant rather than reusing this. Four further things are load-bearing. **The retry is one call, shared by two verdicts, and never `LLMRequestFailed`** — the client has already walked its backoff curve, so asking again spends that user's turn on the same failure. The verdicts are `LLMResponseInvalid` (a body that did not decode, or decoded to something that is not the §7 contract) and, since 2026-08-17, two post-resolution ones: **more than half the named titles resolving to nothing** (`UNBELIEVABLE_UNRESOLVED_FRACTION`) and **more than nine tenths of them being series the user already has** (`IGNORED_EXCLUSION_FRACTION`), both judged only above `MIN_JUDGED_SUGGESTIONS` because a fraction over two entries is noise. The two thresholds are deliberately far apart: an unresolvable title is always a defect, while *some* overlap with the library is not disobedience — resolution is fold-exact with a ±1 year window, so a model-authored title can legitimately land on a different show the user happens to have, and a large library makes that likelier. Nine tenths is the instruction having been ignored wholesale, which is what actually happened the day the title fix shipped. That second one is the same complaint reached one layer later still, which is why **resolution now happens inside the retried attempt** rather than after it, on exactly the reasoning NEU-1109 used to put the parse there: the identical failure must not be retried-or-not depending on which layer noticed. Half is far above anything measured (1 of 25 on a clean profile *and* on a deliberately obscure international one), so it cannot fire on an account the catalog merely covers badly — and since NEU-1173 the incident that motivated it is handled a layer earlier, so what that threshold still stands in front of is an answer naming shows which genuinely are not there, not one naming them badly. **The two differ in what a bad second answer costs, deliberately**: a second unbelievable *body* raises and the user is recorded `failed`, because there is nothing to keep; a second answer that resolves no better is *discarded and the first kept*, because 5 rows beat a `failed` set and a provider failure on the retry must not cost a user the answer the first call already produced. So that path can only improve on the status quo. **Per-user isolation catches every exception, not only `LLMError`**: isolation is about the *user*, not about which layer failed, so a `SQLAlchemyError` while resolving one account must not cost the other four their week; the `failed` row is then written on a **fresh session**, because the one that raised is in an unknown state. **The exclusion filter is the caller's half of a rule the prompt also states** (spec §8) — `excluded_show_ids` is the same object the payload was built from, so it costs no query, and two model-authored titles resolving to one show are collapsed here because `uq_user_recommendation_set_rank` would not catch it. And **a below-floor user accrues one `insufficient_history` row per run**: NEU-1108 settled the regeneration gate on the newest *succeeded* set, so the hash it compares against is never one of those rows. That is the right call there (a gate reading any status would skip an unchanged user forever after one outage) and its cost here is ~52 rows a user a year and zero calls, which is the half §5.4 cares about. Do not "fix" it by widening the gate.

**The never-recommend rule is enforced twice, from one definition.** Project spec §8 — never recommend a show the user already has a record for — used to be enforced only at generation time, in Python, inside `payload.build_payload`. A stored set is immutable, so a show the user added to My Shows on Monday kept one of the twelve cards until Sunday's pass superseded the whole set; four of the five cards on the page were in that state on production 2026-08-17. Since NEU-1175 it is also enforced at read time, by an anti-join in `recommendation_repo.list_current_recommendations`, and **`recommendations/exclusion.py` is the one place the rule is written** — `show_ids_never_to_recommend` for the read path and `load_show_ids_never_to_recommend` for the payload builder, built from the same branches. Six things are load-bearing. **A new source goes in that module and nowhere else**, which is what makes it change both ends at once — NEU-1178's dismissal was exactly that, and it is why the functions no longer carry §8's "has a record for" phrase: a dismissal can name a show the user has never met, so the old name would have misdescribed the module's own contents. That module owns only the *read* of `user_recommendation_dismissal`; `recommendation_dismissal_repo` owns the write, exactly as `show_membership_repo` owns the writes to `UserShowWatch` while the first branch selects from it. **All four §8 sources are the set, not My Shows alone**: `show_membership_repo.add` has one caller, so rating a show, rating an episode or marking an episode watched never creates a My Shows row, and the narrow rule would keep the card for the rest of the week. **Every branch selects a NOT NULL column**, because one NULL inside a `NOT IN` operand makes the anti-join return nothing at all — an empty recommendations page, silently. **The set is never mutated and `rank` is never renumbered**: suppression is a live join, so removing the record brings the suggestion back, and immutability is what makes the weekly swap atomic (§9) and keeps `raw_response` usable as the record of what the model said. **Fewer than twelve is the answer when the 25-asked-for headroom runs out** — nothing is backfilled from an older set. And the payload builder now takes the same set from the same module rather than unioning `taste_for_user`'s keys with an `episode_rating_repo` call: that union was correct only because the taste universe happened to be three of these four sources, so narrowing the universe for a taste reason would have silently narrowed what we never show. NEU-1175 was a swap, so the pass's query count was unchanged, the payload's bytes were unchanged, and **`PROMPT_VERSION` was deliberately not bumped**; NEU-1178's fifth branch changes the bytes for anyone who dismisses something and **does** bump it, to `"5"`, alongside two instruction clauses that asserted everything named in the payload is a series the person already *has* — false for a dismissal, and the second clause made the ban grammatically derive from the false premise.

Six things are load-bearing. **`prompt.quoted_candidate` is where it lives**, not `resolution.py` and not `parse_suggestions`: a dressed title is a response that did not honour §7 rather than a harder catalog lookup, so the knowledge belongs with the module that records how this model breaks its contract — and repairing it in the parser would erase the evidence that it did, while repairing it in the resolver would hand it to every future caller, none of which is reading a model's answer. **The pairing runs from the right**, which is measured rather than tidy: every observed dressed title carries an *odd* number of apostrophes because the connective is a possessive, so pairing left to right recovers `" sibling "` in four cases of four, and on the version-1 answer it recovers `Industry` — the one show the model was explicitly declining *because the user has it*. The leading segment is always the show compared against or declined; the trailing one is always the recommendation. **One candidate, never a walk of every quoted run**, which is the shape §8 refuses: each extra candidate is another chance for a junk segment to land on a real show, and `The Americans` is a real show. **It fires only where `resolve` already answered `None`**, so a show whose real name carries quotes matches itself and never reaches it, and the candidate goes back through the identical `resolve` with the identical year — the ±1 window is what makes a wrong extraction fail closed rather than confidently wrong. **A recovered title counts as resolved**, so it collapses `unresolved` and `UNBELIEVABLE_UNRESOLVED_FRACTION` stops seeing this shape; no threshold replaces it, because `_ask` keeps whichever attempt produced more rows and a "most titles needed recovery, ask again" rule would reliably spend a call and discard its result. **`recovered_from` is what restores that observability by query rather than by tripwire**, which is the same argument this repo has now paid for three times over (`match_method`, `matched_via`, the three sync watermarks) — a signal living only in rotating container logs is the weakest form of it. A failed fallback annotates the unresolved log line with `[tried: …]`, because without it a catalog gap, a wrong extraction rule and the model sending the *leading* show's year print the identical line.
