# Auth, abuse gates and identity rules

> Extracted from `.claude/CLAUDE.md` (2026-08-19) to keep the always-loaded file under the context limit.
> Read before touching signup, login, sessions, the client-address resolution, Turnstile, or `app/schemas.py`'s `DisplayName`.

These are load-bearing and easy to get wrong.

**The client address comes from the right of `X-Forwarded-For`, and hops are the knob rather than Traefik's configuration.** `src/tvbf/client_ip.py` is the one place a request's address is resolved (NEU-1160). Uvicorn runs without `--proxy-headers` in both the compose file and the `Dockerfile`, so `request.client.host` is the proxy for **every** request — which means every use of it before this ticket, `session.ip` and `login_attempt.ip` included, was recording Traefik. Five things are load-bearing. **Right-most, not left-most**: the left-most entry is whatever the client sent and an attacker authors it freely, while the right-most is what the nearest proxy observed — and the rule holds whether that proxy appends to an incoming header or replaces it outright, which is exactly why it is expressed in hops. **`TRUSTED_PROXY_HOPS` defaults to `1` and raising it is a trust decision**, not a tuning knob: each increment moves the boundary one entry left, and a value higher than the number of proxies actually in front of the app hands the throttle key straight to the client. It exists so that putting Cloudflare in front of the API later is a config change rather than a code change. **The value is validated with `ipaddress.ip_address`** because `app.auth_attempt.ip` is `INET` and a junk value raises `DataError` at insert and 500s the request. **`None` means the request is not throttled at all** — absent a trustworthy address the alternatives are one global counter (trivially weaponised into a denial of service against every user) or refusing the request (a self-inflicted outage the first time a header changes shape). And **IPv6 is deliberately not folded to a /64**, which is normally a hole since a residential allocation is a /64 an attacker rotates inside for free: `api.tvbingefriend.com` has an `A` record and no `AAAA` record (checked 2026-08-19), so the hole is unreachable — the day an `AAAA` record is added, fold before the table means anything, because nothing in the code will say so.

**Two auth gates, complementary, and neither substitutes for the other.** The email-keyed lockout in `account_service.authenticate` (5 failures / 15 min, `app.login_attempt`) answers "has this *account* been guessed at?" and is **untouched** by NEU-1160. `app/services/auth_throttle.py` answers "how much has this *address* already done?" — the question credential stuffing walking a different email every request makes invisible to the first, and a hole that was live before open registration was anywhere near it. Six things are load-bearing. **The budget is one frozen `Throttle` dataclass**, for *half* of `rate_budget.Budget`'s reason — a call site states the budget it means and the pair cannot drift across the four settings, while Budget's other half (it is one object because `get_rate_limiter` is `functools.cache`d and keys on the literal call) does not transfer, because nothing here is cached; it lives in `config.py` rather than beside `enforce` only because `Settings` returns it and `db` imports `config`, so config cannot import anything under `app` without a cycle. It was `IpThrottle` until NEU-1162 renamed it — **named for the shape, not for the key**, because the report throttle is keyed on a *user* and NEU-1157 adds a second user-keyed budget of the same shape; the `Settings` properties keep their own names, which is where the key is said. **A request rejected with 429 is not itself recorded**: the window drains and a throttled address recovers unattended, where recording rejections would let a script hold itself banned indefinitely — appealing until the script belongs to a NAT'd office. **A successful login never clears the address's counter**, unlike the email-keyed one, because an attacker owns at least one valid account — their own — and clear-on-success would hand them a reset button between every ten guesses. **Only login *failures* are counted, but every signup is**, successful or not: credential stuffing is made of failures so the login signal is intact while a shared household that logs in successfully never accumulates a count, whereas a signup flood is made of attempts and a bot spraying invalid tokens must burn its five per hour on the rejections. That is why `auth_throttle.record` **commits immediately** — `account_service.signup` calls `db.rollback()` on its `EmailInUse` path, which would otherwise discard the attempt row and make a duplicate-email spray free. And **the 429 leaks what the 401 hides, deliberately**: `authenticate` returns `InvalidCredentials` for a locked-out email precisely so an attacker cannot tell guessing from lockout, while an IP throttle cannot hide, because the SPA renders a distinct message for it — what leaks is a fact the attacker already knows, how many requests they have sent. **The count and the insert are not locked together**, unlike `rate_budget.DatabaseRateLimiter`'s `SELECT ... FOR UPDATE`: requests racing on one address can all read the same count and all pass. Accepted rather than overlooked — the budgets are 5/hour and 10/15min against a bucket that is 20/second, the overshoot is bounded by concurrency rather than unbounded, and a row lock on every signup and failed login would put a serialisation point on the two routes an attacker is already flooding. The throttle has **no switch and is always on**; it is local, needs no network, and the suite truncates `app.auth_attempt` between tests, so it is inert unless a test deliberately exceeds a limit.

**Turnstile fails closed, and its switch is explicit rather than inferred from the secret.** `integrations/turnstile.py` verifies a signup token against Cloudflare's siteverify endpoint (NEU-1160), beside `integrations/linear.py` — this repo's precedent for an outbound call inside a request. Five things. **ADR-0002 is not violated**: that ADR is about *catalog data*, and what it forbids is fetching on a cache miss what a mirror should already hold, so load scales with our traffic instead of our catalog; a captcha token mirrors nothing and is worthless a second time, which is the same reading under which `POST /me/feedback` already calls Linear inline. **Unverifiable means no account** — the availability cost is close to zero because `app.tvbingefriend.com` is Cloudflare-proxied, so during a Cloudflare incident the SPA rendering the signup form is unreachable anyway, and failing open would open the exact hole this closes, in the one window an attacker would most like to have it, invisibly. **The response is read through a Pydantic model, never `payload.get("success")`**: a body that decodes to a *list* — an interception page, a misrouted response — makes `.get()` raise `AttributeError`, which is neither of the two exceptions and escapes as a 500, the same failure `llm/client.py` reads its envelope through `api_payloads.ChatCompletion` to avoid. **`error-codes` is logged and never returned**, because it distinguishes an expired token from a bad secret and the second is our misconfiguration rather than the user's problem. And **`TURNSTILE_ENABLED` is a boolean with a boot check** — `create_app()` raises when it is true with no `TURNSTILE_SECRET_KEY`. Deriving the switch from the credential, the shape `TMDB_READ_ACCESS_TOKEN` and `DEEPINFRA_API_KEY` use, is right for those, where an absent credential disables a job that fails loudly at its call site; here it would mean a secret dropped from the Coolify UI turns signup protection off with nothing anywhere saying so. Off is the default, so `task test` stays offline; **nothing in the repo turns it on**. There is deliberately **no `TURNSTILE_SITE_KEY`** in backend config: the site key is public, is read by exactly one thing — the widget in the SPA, from its own `env.ts` — and a copy here would be read by nothing while sitting ready to disagree with the one the browser uses. `turnstile_token` is likewise **optional in `SignupRequest` and required by the handler when verification is on**, which keeps every existing call site working and puts "enabled means required" in the only place that knows; a missing token is a 400 `captcha_required` rather than a 422, because `api/client.ts` renders field-level 422s against form fields and there is no form field for this.

**A display name may not be an address, and the rule's leading `[^\s@]` is what keeps it out of NEU-1163's way.** `app/schemas.py` owns `DisplayName`, one `Annotated` alias over `BeforeValidator(_strip_display_name)` and `AfterValidator(_reject_email_shaped)`, shared by `SignupRequest` and `MeUpdateRequest` (NEU-1194) — `OptionalDate`'s shape one layer up, and for the same reason: two write sites, one verdict. Four things are load-bearing. **The alias carries the strip as well as the rule**, or the two doors disagree about the rule itself rather than merely about length — `" a@b.c "` would be checked raw at signup and stripped at `PATCH /me` — and it is what makes `"   "` a refusal at both, which it was not at signup before. **`_EMAIL_SHAPED` is `[^\s@]@[^\s@]*\.[^\s@]`, deliberately narrower than the ticket's "contains `@` with a dot after it"**, which would reject `@home with Tom. Really` while the same ticket's own criteria require that class to pass; a leading `@` therefore never matches, which matters because NEU-1163 is making `@handle` a first-class concept and a rule that rejected every string starting with `@` would fight the feature being built one ticket over. **`tom@localhost` and `Tom @home.com` are documented accepts** — no dot, and no local part — because the rule stops a routable address being published rather than parsing one. And **each class keeps its own `Field(...)`**, so the `max_length` 100-vs-80 split between the two sites is untouched: a real inconsistency, a different defect, and one with a live-data question behind it. The migration `b7d3e02c9a41` restates that regex in SQL to rewrite the one production row that predates the rule; it is a **snapshot of the rule as of that revision and not a copy that tracks it**, so a later loosening of the validator leaves it alone — the pass has already run everywhere it will ever run. **The refusal is a bare 422 until NEU-1196 ships**: `api/client.ts` reads `detail` only when it is a string and FastAPI sends a list for schema validation, so the SPA renders `Request failed with status 422` and the user is told only that something failed.

**A third gate: `disabled_at`, which is one predicate at one seam (NEU-1162).** `app.user.disabled_at` is a nullable timestamp — not a boolean, because the question asked of a moderation action later is *when* — and it makes one sentence true: **a disabled account cannot authenticate, cannot mutate its own identity, and is invisible to every user who is not already connected to it.** The sentence is stated without an asterisk on purpose; the emailed-link paragraph below is why it can be. Six things are load-bearing. **The check lives in `account_service.resolve_session_user`, which has exactly one caller** (`deps.get_current_user`), so it covers browse, `/me`, connections, friend engagement, admin and everything added later at once rather than route by route — a disabled user resolves to `None` and gets the **existing `401 auth_required`**, byte-identical to a request with no cookie. **No new status code and no `account_disabled` detail**, which is the more honest domain model and is rejected for the reason AC 3 refuses to tell a disabled abuser at login: a machine-readable confirmation on every request tells them precisely what happened, and they get one per retry; the accepted cost is that a user disabled by mistake sees an unexplained logout and the remedy is a support conversation. **The login check sits *after* `verify_password` and *before* `clear_for_email`** — Argon2 is deliberately slow, so answering a disabled account before it would take milliseconds where every other 401 takes ~100ms, which is a timing oracle saying exactly what the generic error refuses to say; landing before `clear_for_email` is what stops a disabled account being used as a reset button on the email-keyed lockout. **No `app.login_attempt` row is written** on that path, because that ledger answers "is this *account* being guessed at?" and the guess was correct — recording it would poison the brute-force signal; **the IP throttle still records an attempt with no new code**, because `InvalidCredentials` propagates into the router's existing `except` branch. **Reversibility is the property the whole feature buys**: nothing is deleted, copied, backfilled or tombstoned at disable time except sessions, every §4 consequence is a live join, and clearing the flag restores the account exactly, minus the sessions. And **re-disabling someone already disabled leaves the stamp untouched** — it records when moderation began and is the *only* record of the act (there is no `disabled_by` and no `disabled_reason`; the grounds live in the report row and the Linear issue it created), so re-stamping is the one way to destroy the fact of when it happened. Session revocation runs unconditionally whenever `disabled` is true, not only on the transition, which closes the race where a session was minted between the flag being set and the delete landing.

**The three emailed-link paths take a token instead of a session, so the disabled predicate never runs on them and each closes itself.** `POST /reset-password`, `/verify-email` and `/email-change/confirm` refuse a disabled user's *valid* token with their **existing generic `400 invalid_token`** — nothing an abuser can tell apart from an expired one — and the token stays consumed, because it was redeemed. `POST /forgot-password` silently no-ops instead: it already answers `202` unconditionally to avoid enumeration, so the check leaks nothing, and deleting a disabled user's outstanding `auth_token` rows would buy nothing anyway since that route is unauthenticated and they would mint a fresh one a second later. Left open, these are not merely untidy: a disabled user could **verify their email** (the flag that makes an account visible in people search) and **change their email address**, detaching the mailbox that identifies them right before NEU-1158 strips the archive PII.

**Invisibility is four predicates, each a join to `app.user` on `disabled_at IS NULL`, each where a rule of exactly that kind already lives (NEU-1162 §4).** `connection_service.accepted_friend_ids` covers the feed and all four friend-engagement routes; `connection_service.are_connected` covers the friend library via `_require_connected_friend` (which already answers 404 rather than 403, so "disabled" joins "no such user" and "not your friend" as one answer); `user_repo.search` covers people discovery, beside the NEU-1161 verified predicate already there; `connection_repo.list_pending_for_user` covers a request already sitting in a stranger's inbox. All four live in the repo/service layer rather than the routers for the reason NEU-1161 §3.2 gives about `user_repo.search`: `limit` must still return a full page. **`GET /me/connections` is deliberately not filtered** — invisibility to *strangers* is the goal, and an existing accepted friend is not a stranger; hiding the row makes a connection vanish and re-appear for someone who did nothing wrong. Two derived consequences follow from the flag existing rather than from an AC: `user_repo.list_ids` excludes disabled users, so the weekly recommendations pass does not spend a DeepInfra call on an account that cannot see the result, and `forgot-password` no-ops as above.

**A report is persisted, committed, and only then notified — the commit boundary is the contract (NEU-1162 §8.1).** `POST /reports` is `get_current_user` + `require_csrf`, always **204** once the row lands, and `report_service` reuses the feedback flow's *components* — the same `LinearClient` for a single `issueCreate`, the same `send_email` and `email/templates.py` — while adding no second *mechanism*. Five things. **It must not mirror `/me/feedback`'s failure modes**: that route persists nothing, so its 503-when-disabled and 502-on-`LinearError` are honest, whereas a report that mirrored them would either lie ("stored, but here is a 502") or lose data because a third party was down — and note the sharp edge, `linear_feedback_enabled` defaults to `False`, so a mirrored contract would 503 every report in local dev and CI. **The route reads `request.app.state.linear_client` directly and never depends on `get_linear_client`**, which raises 503 when unconfigured and would undo exactly that. **No `customerUpsert` and no `customerNeedCreate`** — those model "this customer wants this" and feed the customer-requests view that ranks product demand; a report is a complaint about a third party, so filing it that way corrupts the signal that view carries. **The issue title carries the reported user's id, never their display name**, which is attacker-authored where a report title is read under time pressure; the name is in the body as context. **A notification failure logs at ERROR, not `feedback_service`'s `warning`** — Sentry is initialised in `main.py`, so ERROR is a real alert, and a dropped notification was, until NEU-1197, the only way a report went unseen. The ERROR level survives that ticket: `GET /admin/reports` is now the backstop the log line was standing in for, but it is a queue someone has to open, where the alert arrives on its own. Linear being *unconfigured* logs at warning instead, because that is the configured state in local dev and CI. **The throttle's ledger is `app.user_report` itself** — 5 per 24 hours per reporter, `REPORT_THROTTLE_MAX` / `REPORT_THROTTLE_WINDOW_MINUTES` — because every report is persisted anyway, so there is no `auth_attempt`-style side table and no "record the attempt" step to get wrong; the un-locked count/insert race is inherited from `auth_throttle.enforce` and accepted for the reason stated there. **Reporting requires no verified email, and blocks do not suppress it in either direction**: NEU-1161's rule is that a verified mailbox is the price of *outreach*, and a report touches Tom rather than the reported user — gating it would silence the newest users, who are exactly who a griefer targets. A disabled user can be reported; §4 makes them invisible, not nonexistent.

**The report queue filters nothing, and that is the rule most likely to be "fixed" by mistake (NEU-1197 §4).** `GET /admin/reports` joins `app.user` twice and carries none of §4's four `disabled_at IS NULL` predicates. Those predicates are about what a **stranger** may see; this is the one read path whose entire purpose is to see what strangers cannot. Four cases, all kept deliberately: a report **about** a disabled account stays listed, because hiding it hides the reports about precisely the accounts under moderation — and the queue answers "has this already been dealt with?" only by showing the report *and* the `disabled_at` beside it; a report **by** a disabled account stays listed, because disabling a griefer must not retroactively erase the reports that justified it; reports about or by an **admin** stay listed, since §7.1 already lets an admin disable another admin and a queue blind to those would be the one hole in the moderation surface; and self-reports do not exist at all, refused at the write path with `400 cannot_report_self`. The `disabled_at` it shows is a **live join**, never a flag stored on the report, for the same reason §4's predicates are: it cannot drift, and clearing the flag restores the truth with no backfill. `test_reports_about_and_by_a_disabled_user_are_both_listed` is what stands between a helpful reader and a queue that hides the reports it exists to surface.

**A fourth gate, and the first keyed on outreach rather than on identity: the connection-request budget (NEU-1157).** `POST /connection-requests` had no budget of any kind, and once signup stops requiring an invite code (NEU-1156) it is the primary harassment vector — the existing defences all miss it, because blocking is reactive, `require_verified_user` costs a mailbox per *account* and nothing per request, and the IP throttle governs signup and login rather than outreach. It is governed through `app.connection_request_log`, because `app.connection` is deleted on both decline and cancel and therefore retains no evidence a request happened. Seven things are load-bearing.

**Two budgets read one ledger.** The **daily cap** counts requests *created* in a rolling 24 hours — all five outcomes count, so cancel-and-re-send is worthless as a reset — and the **ceiling** that cap is measured against is one of two `Throttle`s, `MAX` (10/day) normally and `FLOOR` (2/day) when the reputation rule fires. `config.Throttle` is reused unchanged rather than grown a third field: NEU-1162 §6.1 renamed it from `IpThrottle` *naming this ticket as the reason*, so `Settings` exposes two properties of that one type and `current_ceiling` returns one of them — the rule then reads as *selecting between two budgets*, and the count/window pair still cannot drift apart at a call site. The four reputation knobs get their own frozen `ReputationRule` for `Throttle`'s stated reason.

**The rule is a rate, not an absolute count, and it demotes rather than earns.** Over 30 days, `adverse` is `declined` + `blocked` + *ignored* (still `pending` past 14 days) and `sample` is `accepted + adverse`; the floor applies when `sample >= 5` **and** `adverse * 100 >= sample * 50`, evaluated in integer arithmetic so the boundary is exact rather than a float rate to argue about. `MAX - adverse` is simpler and needs no minimum sample but demotes a popular user who sent 30 and had 25 accepted — to a subtraction rule volume and rejection are one axis, which is the distinction this exists to draw. **Earn-your-ceiling** (start at the floor, acceptances raise it) is strictly the stronger posture and the only shape that bounds a day-one spammer before any signal accrues; it was rejected as a product decision, because it taxes the honest new user hardest exactly when the app needs them to build a friend graph. **The consequence is recorded rather than hidden: a fresh account runs its first day at the full ceiling**, so the choice of `MAX` carries the security weight rather than the rule does.

**Three exclusions each have a reason that will look like an oversight later.** `cancelled` moves neither numerator nor denominator — the cap already makes cancel-and-re-send worthless, so counting it as a rejection charges twice for one act and reaches the honest user fixing a mistake, while the spammer has no reason to cancel at all. Young `pending` rows are in neither bucket, or every account's rate would be dominated by requests nobody has had a chance to answer and an honest burst would self-demote within minutes. And both windows anchor on **`created_at`, never `resolved_at`**, so a row's membership is stable and the rate is a statement about *sending* behaviour; the leak that a day-29 request declined on day 31 never counts is accepted, because fixing it by anchoring numerator and denominator differently draws them from two populations, which is correct on the day it is written and indefensible six months later. The knowingly-open hole: an account can send its daily ten, cancel all ten, and its rate is unmoved. Acceptable because *the daily cap is what bounds harm* — the reputation rule only lowers that cap.

**The check order is the non-oracle property, and reordering it is the mistake.** **429 → cooldown 409 → 404 → 400 → pair 409 → 201**, with the throttle before the addressee lookup, the self check and the pair check. Checked last, an account at its cap would get `409` for anyone it already has a relationship with (or who blocked it) and `429` for everyone else — a free, silent oracle, with no request created, nothing in an inbox and no cost. That probe exists today but is *not* free: telling `409` from `201` means creating a request the target can see. The accepted cost is that a caller at their cap who requests themselves gets `429` rather than `400`.

**The decline cooldown closes the targeted case, and it was scope growth from a wrong premise.** The ticket claimed the existing 409 stopped re-sending to the same person; it does not — `delete_pending_request` **deletes** the `connection` row, so `find_pair` returns `None` and the same request succeeds, meaning a requester could send their whole allowance to one person who said no, every day, forever. A request to someone who declined the caller within 30 days is refused with **the same vague `409 connection_exists`** the pair check gives, so the caller cannot tell it from "already related" or "blocked", and it leaks nothing new — a requester already learns of a decline by watching the request vanish from `GET /me/connection-requests`. It applies to `declined` only: not `cancelled` (your own withdrawal must not lock you out of correcting it) and not `blocked` (the `blocked` row persists in `app.connection`, so `find_pair` already 409s that pair). Bounded rather than permanent, because `block` is the recipient's explicit permanent tool and a permanent decline converts a soft no into a hard one the decliner never chose. Its window is **its own knob**, not a reuse of the reputation window despite both defaulting to 30 days.

**The ledger writes live in `connection_service`, beside the transitions they mirror** — putting them in the throttle module would mean `block()` importing a throttle in order to record a block. `block` is symmetric in the code and asymmetric in meaning: the *addressee* of a pending request blocking records `blocked`, the strongest unwanted signal available, while the *requester* blocking someone they asked records `cancelled`, because they withdrew and charging them an adverse outcome for their own disengagement is backwards. `cancelled` stays distinct from `declined` and `blocked` from both, since every conflation made now is a measurement that can never be taken later. **Outcomes are terminal**: `unblock` and `remove_connection` write nothing, and reverting a `blocked` row was rejected as either incoherent (to `pending` — there is no request to revert *to*, and it would immediately start aging toward *ignored*) or as laundering an adverse signal on the strength of the victim's gesture (to `cancelled`). The mark rolls off in 30 days regardless, which is automatic forgiveness of about the right size.

**Every writer must tolerate a missing ledger row and no-op, never raise.** Three ordinary situations reach "update the row for this pair" and find nothing: a request predating the migration, a row already cascaded away by an account deletion, and a `block` where no request ever existed — the common case for `block`. `resolve` is an `UPDATE` matching zero rows for exactly that reason; `scalar_one()` there turns an ordinary accept into a 500. Two further rules carried from the throttles it mirrors: **nothing refused writes a row or spends budget** (429, cooldown 409, 404, 400 and pair 409 all create nothing), and the count/insert race is inherited from `auth_throttle.enforce` and accepted for the reason stated there — **do not add `SELECT ... FOR UPDATE`**, which would put a serialisation point on the route an attacker is already flooding.

**Nothing about the budget is exposed to the client** — no `X-RateLimit-*` headers, no field on `GET /me`, no introspection route. Exposing the *limit* exposes the ceiling, and the ceiling is where the reputation verdict is written: an account told "your limit is 2" has been told the tightening fired, which is feedback a spammer tunes against. The accepted cost is that the honest user meets an unexplained wall, which is tolerable only because an honest user sends roughly ten requests in their lifetime — and it means a future frontend ticket has thin material to write copy from.
