# Endpoint surface (annotated)

> Extracted from `.claude/CLAUDE.md` (2026-08-19) to keep the always-loaded file under the context limit.
> The full per-route account, including why each route carries the cache header, per-user field and status codes it does. `CLAUDE.md` keeps only the path index and the auth model. Read this before adding, changing or removing a route.

### Endpoint surface

- **Health:** `/healthz` (liveness — 200 if process is responding), `/readyz` (readiness — 200 if the process can `SELECT 1` against Postgres; 503 otherwise).
- **Push (unauthenticated):** `GET /push/vapid-public-key` (NEU-1484, project spec §5.4) → `{"public_key": "<base64url>"}`, the key the SPA passes to `PushManager.subscribe` as `applicationServerKey` — fetched, never hard-coded, so a rotation is an env change (§7). **`Cache-Control: public, max-age=86400`, the one `public` header in the API**: it is the same value for every caller and describes no user, which is exactly what browse's `private` exists to rule out, and a day is how long a rotation takes to reach a browser that already has it — absorbed by the delivery job's 404/410 retirement anyway. **503 `vapid_not_configured` unless all three of `VAPID_PRIVATE_KEY` / `VAPID_PUBLIC_KEY` / `VAPID_SUBJECT` are set**, not merely the public one: handing out a key the server cannot sign with would let the SPA create subscriptions nothing ever delivers to. The 503 carries no cache header. Router `routers/push.py`, which also holds the per-user `/me/push/*` routes below.
- **Push subscriptions (`get_current_user` dep, mutating routes also `require_csrf`):** `GET /me/push/subscriptions`, `POST /me/push/subscriptions`, `DELETE /me/push/subscriptions/{id}`, `DELETE /me/push/subscriptions` (NEU-1485, project spec §5.4). In `routers/push.py` rather than `me.py`, beside the key they are made against. **`GET` answers `[{id, user_agent, created_at, last_success_at}]` and never the endpoint or the keys** — the endpoint is a capability URL anyone holding it can push to, and the SPA's device list needs only the user agent to derive a label from. **`POST` takes `PushSubscription.toJSON()` verbatim** (`endpoint`, `keys.p256dh`, `keys.auth`; `expirationTime` is ignored) and answers `201 {id}` whether or not the row existed, because it **upserts on `endpoint` onto the caller** — browsers re-issue the same endpoint after a `pushsubscriptionchange`, and a device that changed hands should follow its current login. **An endpoint another user holds is deleted and re-inserted, not re-owned**, so the new owner gets a fresh id — keeping it would let the previous owner's delivery rows, via `uq_push_delivery_key_subscription`, skip the new owner for a notification already sent that day. The caller's own endpoint updates in place, keeping its id, with `failure_count` reset because the keys are new. It stores the request's `User-Agent`, and refuses a non-`https` endpoint with 422, since the delivery job POSTs to whatever is stored. **503 `vapid_not_configured`** on the public-key route's terms — checked after auth and CSRF. `DELETE /me/push/subscriptions/{id}` is 204, or 404 `not_found` for an id that is not the caller's whether or not it exists; the collection `DELETE` is the "turn everything off" switch, 204 even when there was nothing. Deleting a subscription never deletes its delivery log rows — `app.push_delivery.subscription_id` is SET NULL.
- **Export's push half:** `GET /me/export` (in `routers/me.py`, streamed by `export_service`) appends `push_subscriptions` — each in `GET /me/push/subscriptions`' shape, `{id, user_agent, created_at, last_success_at}`, newest first, **never the endpoint or the keys** — and `notification_preferences`, the five `notify_*` flags (NEU-1493, project spec §7). The export exists to be complete; the endpoint and keys are capability secrets, not the user's data.
- **Push test (`get_current_user` + `require_csrf`):** `POST /me/push/test` (NEU-1486, project spec §5.4) — body `{"subscription_id": UUID}`, pushes the §5.3 `test` payload (`title` "TV BingeFriend", `body` "Notifications are working", `url` `/settings`) to that one device **synchronously, in the request**: it is one user-initiated push and the user is watching for it, which is spec §7's carve-out from ADR-0002. **`202 {status, status_code}` reports the outcome rather than hiding it** — `sent` with the push service's status, or `failed` with its status (`null` for a transport error). **`410 {status: "gone", status_code}` when the push service answers 404/410**: the subscription is deleted, and the SPA drops its local one. 404 `not_found` for an id that is not the caller's; 503 `vapid_not_configured` first. It logs a `push_delivery` row, `kind='test'`, key `test:{subscription_id}:{unix_ts}`, **committed `pending` before the send** and flipped after it — a second transaction so no pooled connection is held across the push service call and a concurrent request's throttle count sees the row. **Throttled at `PUSH_TEST_THROTTLE_MAX` (5) per `PUSH_TEST_THROTTLE_WINDOW_MINUTES` (60) per user, `429 rate_limited` + `Retry-After`**, with `app.push_delivery` itself as the ledger on `user_report`'s precedent — the row survives the subscription, so retiring a device does not refund the budget. A second test to the same device in the same second collides on the key and is also a 429 (`Retry-After: 1`). A `sent` stamps `last_success_at` and resets `failure_count`; a `failed` does **not** increment it, since that count is the delivery job's retirement rule and a user pressing the button on a bad connection should not retire their own device. Service `app/services/push_test_service.py`.
- **Browse (user-gated via `get_current_user` at the router level, `Cache-Control: private, max-age=300` by default with per-route `private, no-store` overrides, CORS allowlisted):** `GET /shows` (list with search/filters/sort/pagination; items are `BrowseShowOut` — `ShowSummary` plus `my_rating` and, since NEU-1185, `in_my_shows`, which marks a show the viewer already tracks and never filters it out of search results), `GET /shows/{id}` (detail with embedded seasons), `GET /shows/{id}/seasons`, `GET /shows/{id}/episodes?season=N`, `GET /episodes/{id}`, `GET /genres`, `GET /networks`, `GET /shows/{id}/similar` (NEU-1053 — TMDB's "More like this" from `catalog.show_recommendation`, top **12** after filtering `adult` and `deleted_upstream_at` **at read time** on NEU-1108's precedent, in TMDB's own rank order. `SimilarShowOut`, so the SPA reuses `ShowCard` / `ShowGrid` unchanged. Since NEU-1185 it carries **`in_my_shows` and `my_rating`**, and the header moved with them: NEU-1053 declined both per-user fields to keep a body byte-identical for every viewer behind the cacheable router-level header, and the mark spends exactly that — the alternative was the one grid in the app that knows you track a show and declines to say so. Once spent, only the cost of a query still stood against `my_rating`, so it is filled too; the route now takes `_SHOW_EP_CACHE` (`private, no-store`), on `/trending`'s reasoning that a mark the user can toggle must not be readable back out of the browser cache. **`genres` and `network` stay empty**, unchanged and not re-decided: `ShowCard` renders neither, so hydrating them is two more round trips for fields nothing displays. A show with no rows answers `200 []` (~8% of the long tail, and the SPA renders no section); an unknown show still 404s, on `/cast`'s reasoning that an empty result cannot stand in for a missing show), `GET /trending` (NEU-1056 — the `catalog.trending_show` snapshot NEU-1055 writes, in TMDB's rank order, as `{"captured_at", "shows"}`. **The seven-day staleness cutoff is the server's rule and lives in one function** — `browse_queries.get_trending_snapshot` applies it *in the query*, so no path returns a row past it, and the SPA must never re-implement it: a rule enforced in two places drifts, into week-old rows under a label reading "trending right now". `captured_at` is null exactly when `shows` is empty, so a withheld snapshot's age is not reported and the cutoff cannot be re-derived from the payload; a stale snapshot and an empty table are the same body, and both render as no section. Shows in the viewer's My Shows are **marked** (`in_my_shows`) **and never filtered** — which makes the payload per-user, so this route takes `no-store` rather than the router-level header, and *that* is what pays for `my_rating` here — the argument `/similar` then reached the same way (NEU-1185). `genres` and `network` stay empty on `/similar`'s reasoning. Contract published at `docs/specs/NEU-1056-trending-contract.md`)), `GET /anticipated` (NEU-1059 — the shows premiering soonest that most people are waiting for, a **bare array** of `ShowSummary` + `in_my_shows` over NEU-1058's live `list_anticipated_shows` query. A bare array rather than `/trending`'s object because nothing is stored, so there is no `captured_at` to wrap alongside the list — and for the same reason **no staleness cutoff**, which "anticipated" also does not need, carrying no present-tense claim a week-old answer would falsify. Freshness is structural: `first_air_date >= current_date` is evaluated on the read, so a show cannot linger after it premieres and no job's failure can leave a stale list. Shows in the viewer's My Shows are **marked and never filtered**, which makes the payload per-user and takes `no-store` — the ticket asked for `public, max-age=300` alongside the mark and the two cannot both be had, `/trending`'s resolution. (That phrasing is NEU-1059's own, and it was wrong twice over about the code it was describing — the browse default has always been `private`, never `public`, and the helper is `_set_browse_cache` rather than the `set_cache_control` the ticket names. It is quoted here as the request that was made, not as a description of the router.) **`my_rating` is null here where `/trending` fills it**: every entry premieres in the future, so the missing-badge argument does not reach it, and the acceptance criterion is one query for the list plus one for the mark. `genres` and `network` stay empty on `/similar`'s reasoning. Contract published at `docs/specs/NEU-1059-anticipated-contract.md`). `GET /people` is person search (NEU-950): search-only — no usable token is an empty page, never the whole table — and ordered by **Popularity**, then case-insensitive name, then id, unscored people last, with no `sort` parameter (NEU-1513). Person scores move only when a show crediting them is re-mirrored, so they are of mixed vintage; accepted.
- **Credits (browse router — user-gated, router-level `private, max-age=300`, no per-user field on any of them, so no `no-store` override):** `GET /shows/{id}/cast`, `/shows/{id}/guest-cast`, `/shows/{id}/crew`, `/shows/{id}/episode-crew`, `/shows/{id}/seasons/{number}/cast`, `/shows/{id}/seasons/{number}/crew`, `/episodes/{id}/guest-cast`, `/episodes/{id}/crew`, and the person's `/people/{id}/credits`. Kept off the detail routes because they are unbounded (Law & Order holds 11,550 show cast rows). **Since NEU-1512 each route answers what one panel renders, and the server decides who is a regular** (`docs/specs/NEU-1512-list-full-episode-cast.md` §4): a **regular credit** is a (person, character) with a `catalog.season_cast` row on one of the show's seasons, read off upstream's own per-season list rather than inferred; `/cast` is those, once each however many seasons, and `/guest-cast` is every other `show_cast` row, so the two **partition `show_cast`** — a regular who guested in another season as the same character is one aggregate row, and a regular's. `/cast` adds the one row `show_cast` lacks: a regular upstream's aggregate omits, sorted last with `episode_count: null`. A **series crew credit** is a `show_crew` job whose aggregate `episode_count` exceeds the person's `episode_crew` rows in that role on that show (`coalesce(count, 0) > rows`): `/crew` is those, `/episode-crew` the rest — a director of forty episodes holds an aggregate of forty, a sum the episode rows already list. Crew keeps the derivation because season-grain crew is not ingested. **Every cast and crew entry carries `episode_count`**: the aggregate on the show routes, in-season appearances for a season's guests and crew, and **null** for a season's regulars (TMDB credits a regular on every episode of the season — a claim, not a count) and on the episode routes (one appearance). The season routes take the season **number**, as `/shows/{id}/episodes?season=N` does, resolve the row through `catalog/seasons.py:deduped` so a duplicated number picks what `/shows/{id}/seasons` lists, scope episodes by `(show_id, season_number)`, and **404 an unknown season** — the season is the parent here, where on `/episodes` it is a filter; season 0 is served like any other. `/seasons/{number}/cast` answers `{regulars, guests}`: regulars in billing order, guests grouped per (person, character) by appearances, minus any pair the season's own regular list holds (upstream inconsistency; the season wins at season grain). The episode routes are unchanged but for the null `episode_count`: TMDB does not know whether a regular is in a given episode, so the episode page links to the season's cast rather than repeat one unverifiable block. `/people/{id}/credits` keeps its four always-present lists; `cast` is regular credits only — one per (show, character), with `episode_count`, `seasons` (ascending) and `last_credited` (the latest air date over those seasons' episodes), most recently credited first, nulls last — and `crew` is series crew only, with `episode_count`; a guest-only show appears only in `guest_cast`, and the SPA merges the lists per show. Every route 404s an unknown parent, because an empty list is ordinary (27% of shows have no cast).
- **Auth (cookie-session + CSRF):** `POST /signup` (requires invite code and, since NEU-1163, a **required `handle`**), `POST /login`, `POST /logout`, `POST /password-change`. Session set via httpOnly cookie scoped to `.tvbf.localhost`; CSRF token returned in body and required on mutating `/me/*` requests via `X-CSRF-Token` header. Signup and login additionally carry NEU-1160's two abuse gates — an always-on IP-keyed throttle (**429 `rate_limited`** with `Retry-After`) on both, and Turnstile verification on signup alone (**400 `captcha_required` / `captcha_invalid`**, **503 `captcha_unavailable`**), off by default and enabled only in the Coolify UI. See the two non-obvious patterns below. Since NEU-1162, `POST /login` also refuses a **disabled** account with the same generic `401 invalid_credentials` a wrong password gets — checked after `verify_password` so the timing does not say what the error refuses to — and every session-bearing route refuses one with the existing `401 auth_required`, byte-identical to a request carrying no cookie. Signup's handle refusals split three ways and the split is the contract NEU-1169 renders against: **422 with `loc: ["body", "handle"]`** for everything `schemas.Handle` decides (charset, the 3–30 length bounds, the leading-letter rule, the reserved-word blocklist and the `user_<8 hex>` pattern), **409 `handle_unavailable`** for a handle a live account holds *or* one a different account released — byte-identical for both causes on purpose, since distinguishing them turns a signup-adjacent surface into a *has this handle ever existed* oracle including for deleted accounts — and **409 `email_in_use`** unchanged for the email. That last pair is why `account_service.signup` dispatches its `IntegrityError` on the constraint name: with `uq_user_handle` beside `uq_user_email`, the old blanket handler would report `email_in_use` for a duplicate handle, on the one form submitting both. `409` rather than a synthesised 422 for the conflicts because it matches `email_in_use`, the same class of thing on the same form. Case and a leading `@` are **normalised, never refused** — `TomBoone`, `@TomBoone` and `  @tomboone ` all store `tomboone`.
- **Me (`get_current_user` dep, mutating routes also `require_csrf`):** `GET /me`, `PATCH /me/handle` (NEU-1163), `DELETE /me` (account delete), `GET/PUT/DELETE /me/shows` and `/me/shows/{id}` (My Shows membership), `GET /me/watch-next`, `GET /me/upcoming`, `GET /me/upcoming/seasons`, `GET /me/upcoming/shows`, `GET /me/shows/{id}/episodes/watched`, `GET /me/shows/{id}/seasons/progress`, `POST/DELETE /me/episodes/{id}/watched`, `POST/DELETE /me/shows/{id}/season/{n}/watched`, `POST/DELETE /me/shows/{id}/watched`, `PATCH /me/preferences` (partial update answering `AuthedUserOut`: `activity_feed_enabled` since NEU-180 and, since NEU-1490, the five per-kind push opt-outs `notify_airs_today`, `notify_premiere_set`, `notify_premiere_moved`, `notify_ended`, `notify_revived` — all optional, all default on, and `AuthedUserOut` carries all five, so `GET /me`, signup and login return them too; every route answering it builds it through `AuthedUserOut.from_user` so a new field cannot be missed at one of them), `PATCH /me/shows/{id}/hide-from-activity` (NEU-180, `{hide_from_activity}`) and `PATCH /me/shows/{id}/mute` (NEU-1490, push project spec §5.4, `{muted}`) — the two per-row flags on `app.user_show_watch`, same shape: `204`, `404 not_in_my_shows` when the show is not in the caller's My Shows, and `GET /me/shows` entries carry both. **Mute silences every push kind for that show and is deliberately not a never-recommend source** — `recommendations/exclusion.py` does not read it, and muting invalidates nothing on the recommendations side, `POST /me/recommendations/{show_id}/dismiss` (NEU-1178 — never recommend this show to this user again. `POST …/dismiss` rather than `DELETE /me/recommendations/{show_id}`, because the request *creates* a row, the show need not be in the collection at all, and the effect outlives the set the collection is. Idempotent `204`, `404` only for a show id no `catalog.show` row has, and **no un-dismiss**; the show need not have been recommended, so a show found by search is dismissible. Deliberately emits no `activity_event` — `my_shows_service.add` minus the emit), `GET /me/recommendations` (NEU-1112 — the newest `succeeded` set's suggestions, capped at 12 and `adult`/`deleted_upstream_at`-filtered **on the server**, `Cache-Control: no-store`; empty is `200 {"recommendations": []}` and never a 204, so the SPA can tell "nothing to show" from "the request failed" by status code. **`reason` is written and never served, since 2026-08-17**: `ShowCard` had one truncated 10px line for it, which is not room for a sentence, so serving it put model-authored prose on the wire for nothing to render. It stays in `app.user_recommendation.reason` and in the set's `raw_response` as a diagnostic, and it is still *asked for* — removing it from the prompt is the riskier change, because `reason` is where the model puts its explanations and the run above is what happens when it has nowhere to put them. Contract published at `docs/specs/NEU-1112-recommendations-page-contract.md`). **`PATCH /me/handle` is its own route rather than a field on `PATCH /me`**, and the reason is the throttle: widening `MeUpdateRequest` into a partial update to carry a rate-limited field beside an unthrottled one is how a display-name save ends up refused by a `429` about a handle the user did not touch. It answers `AuthedUserOut`, takes the same 422/409 vocabulary signup does, and adds **429 `rate_limited` with `Retry-After`** at **3 changes per 30 days** — thirty days because the concern is identity stability rather than load, three because a new user fixing a typo and then fixing their mind should not be locked out for a month. Its ledger is `app.handle_release` itself, so a change writes the release row for the old handle **in the same transaction** as the update: a commit that moved the handle without recording the release would free it silently, which is the one way the never-reusable rule can be broken from inside. Setting the handle you already hold is a no-op that spends no budget. **`DELETE /me` also writes a release row**, before the user row goes, so the handle ends up owned by nobody rather than freed — without it, self-service deletion would be a supported route to handing your identity to a stranger.
- **Connections (`get_current_user` dep, mutating routes also `require_csrf`):** `POST /connection-requests`, `GET /me/connection-requests`, `POST /connection-requests/{id}/accept`, `DELETE /connection-requests/{id}`, `GET /me/connections`, `DELETE /me/connections/{user_id}`, `POST /me/blocks/{user_id}`, `DELETE /me/blocks/{user_id}`, `GET /me/blocks`. Since NEU-1161 **`POST /connection-requests` alone takes `require_verified_user`** (`deps.py`, built on `get_current_user`, **403 `email_not_verified`**): a verified mailbox is the price of *outreach*, never of consumption, defence or withdrawal — so accepting, declining, cancelling, blocking and disconnecting all stay open to an unverified account, and putting the gate at router level is the mistake that breaks accepting. The requester is checked and the **addressee never is**, which is what keeps accept-while-unverified reachable. The other gated surface is discoverability rather than a route: `GET /users/search` answers a normal `200` for an unverified caller but **excludes unverified users from its rows**, blanket, including people the caller is already connected to (they stay reachable through `/me/connections`, and their library still resolves through `/users/{id}/shows`). That predicate lives in `user_repo.search`'s SQL, not the router, so `limit` still returns a full page. Full account, including the error contract NEU-1167 cites and why no backfill migration ships: `docs/specs/NEU-1161-a-verified-email-as-the-price-of-social-access.md`. Since NEU-1157 that same route also carries the **per-requester budget**, and its check order is load-bearing: **429 → cooldown 409 → 404 → 400 → pair 409 → 201**. The throttle runs *before* the addressee lookup, the self check and the pair check, so at the cap every target answers an identical `429 {"detail": "rate_limited"}` with `Retry-After` — checked last it would be a free, silent oracle (`409` for anyone already related to you or who has blocked you, `429` for everyone else, nothing created, nothing in an inbox, no cost), where today telling `409` from `201` costs a request the target can see. The cost accepted: a caller at their cap who requests *themselves* gets `429` rather than `400`. A request to someone who **declined** the caller inside the cooldown answers the *same vague* `409 connection_exists` the pair check gives, deliberately indistinguishable from "already related" and "blocked". **Nothing about the budget is exposed** — no `X-RateLimit-*`, no field on `GET /me`: exposing the limit exposes the ceiling, and the ceiling is where the reputation verdict is written. `POST /connection-requests/{id}/accept` and `DELETE /connection-requests/{id}` are never throttled; only creation is. Full account: `docs/specs/NEU-1157-rate-limit-outgoing-connection-requests.md`.
- **Reports (`get_current_user` + `require_csrf`):** `POST /reports` (NEU-1162 — body `{"reported_user_id": UUID, "reason": str}`, reason 1–5000 chars matching `FeedbackIn.body`. **`204` once the row is committed, whatever the notification path does afterwards**: `report_service` persists, commits, and only then attempts the Linear issue and the maintainer email, so the reporter is told "received" exactly when we have genuinely received it. That is deliberately *not* `/me/feedback`'s shape — that route persists nothing, so its 503-when-disabled and 502-on-`LinearError` are honest, whereas mirroring them here would either lie or lose data because a third party was down, and `linear_feedback_enabled` defaults to `False`, so a mirrored contract would 503 every report in local dev and CI. **`400 cannot_report_self`**, **`404 reported_user_not_found`**, **`429 rate_limited`** + `Retry-After` at 5 reports per 24 hours per reporter (§6). **No `require_verified_user`** — a verified mailbox is NEU-1161's price of *outreach*, and a report touches Tom rather than the reported user; gating it would silence the newest accounts, which is exactly who a griefer targets. Blocks do not suppress reporting in either direction, and a **disabled** user can be reported — §4 makes them invisible, not nonexistent. The rows it commits are read back by `GET /admin/reports` (NEU-1197), which is the backstop for the notification being the part allowed to fail.)
- **Admin users (cookie-session, `require_admin_user` + `require_csrf`):** `GET /admin/users`, `PATCH /admin/users/{user_id}/admin`, `PATCH /admin/users/{user_id}/disabled`. Distinct from the bearer-token admin surface below — these are addressable from the SPA by an admin. The disabled toggle (NEU-1162 §7.1) takes `{"disabled": bool}` and answers `AdminUserOut`, which gained **`disabled_at`** so the list shows moderation state (`UserOut` and `AuthedUserOut` deliberately did not — a disabled user cannot reach either, and a field saying so would be the machine-readable confirmation §2.2 refuses to hand an abuser). **`403 cannot_disable_self`** mirrors the existing `cannot_demote_self` guard; **`404 user_not_found`**. Three edge behaviours are deliberate: re-disabling an already-disabled user **leaves the original stamp**, because it records when moderation began and is the only record of the act; **session revocation runs whenever `disabled` is true**, not only on the transition, closing the mint-between race; and **an admin may disable another admin**, because blocking that would protect a rogue admin from the only remedy that exists. Nothing cascades — reversibility is the whole point, against a `DELETE /me` that is not reversible.
- **Admin reports (cookie-session, `require_admin_user`, no CSRF — it is a GET):** `GET /admin/reports` (NEU-1197). The queue reader for `app.user_report`: `POST /reports` commits and only *then* notifies best-effort, so a notification that failed leaves a report visible nowhere, and every ordinary question about the table — has this account been reported by five different people, what did the reporter actually say — otherwise needs a psql session. Cookie-session gated like the neighbour above, not bearer-token gated: an admin reads this in the SPA. `page` (`ge=1, le=1000`) / `per_page` (`ge=1, le=100`) are `GET /shows`'s bounds verbatim and the body is `ShowListPage`'s shape, so the API carries one pagination vocabulary; `total` is load-bearing rather than decorative, because without it `?reported_user_id=` degrades to "at least N" exactly when the number is alarming. Rows are `ORDER BY created_at DESC, id DESC` — the tiebreak is not decoration, since `created_at` defaults to transaction-start time and a pair sharing one can otherwise appear on two pages or on neither. Each row carries both parties as nested refs (`id`, `display_name`, `disabled_at`) and the `reason` **in full and verbatim** — untruncated because reading the reason is the point, unescaped because escaping belongs to the renderer. **Neither party's email**, which `GET /admin/users` already exposes and nobody triages on. **It filters nothing** — NEU-1162 §4's four `disabled_at IS NULL` predicates are about what a stranger may see, and this is the one read path whose purpose is to see what strangers cannot; reports about *and* by a disabled account both stay listed. An unknown `reported_user_id` is `200` with `total: 0`, never `404`. **`Cache-Control: private, no-store`**, the first admin route to carry a cache header: the payload's `disabled_at` mutates through `PATCH /admin/users/{user_id}/disabled` in the same SPA seconds earlier, so a cached body answers "has this been dealt with?" wrongly. `GET /admin/users` has the identical exposure and is a known gap, not a considered difference. Nothing here writes: triage stays in Linear (NEU-1162 §5).
- **Admin push stats (cookie-session, `require_admin_user`, no CSRF — it is a GET):** `GET /admin/push/stats` (NEU-1493, project spec §5.4), in `routers/admin_push.py`. Answers `{subscriptions, users_subscribed, by_day: [{day, sent, failed, retired}]}`: the first two are live counts over `app.push_subscription` (rows, and distinct `user_id`s), `by_day` is **exactly 30 UTC days ending today, oldest first, zero-filled** so the admin panel charts it without gap handling. Days bucket on `push_delivery.created_at` in UTC, which is when a delivery was last *claimed* — a retry re-dates its row. `sent` and `failed` count those statuses; `pending` and `skipped` count nowhere. Every `kind` counts, `test` included — a `POST /me/push/test` that gets 404/410 retires its subscription exactly as the job does, and is counted as one. **`retired` is a subset of `failed`**: the rows with `error IN ('gone', 'failure_limit')` (`push_delivery_repo.RETIREMENT_ERRORS`), which survive the subscription delete because `subscription_id` is SET NULL (§4.3) — so a retirement is counted off the delivery row that recorded it, with **no new table and no extra column**. The 90-day purge never reaches the 30-day window. Read-only; `403 admin_required` for a non-admin session, `401` with none. **`Cache-Control: private, no-store`**, on `GET /admin/reports`' precedent: the counts move every delivery run and every device toggle.

Liveness is `status='running'` *plus* `COALESCE(last_progress_at, started_at)` inside `INGEST_STALE_RUN_MINUTES` — the staleness clause matters because `mark_stale_runs_cancelled` fires only in the lifespan hook, so a run whose process died reads `running` until the next restart and an unqualified check would wedge that kind until a redeploy.
