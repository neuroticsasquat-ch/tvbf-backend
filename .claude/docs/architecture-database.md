# Database topology (annotated)

> Extracted from `.claude/CLAUDE.md` (2026-08-19) to keep the always-loaded file under the context limit.
> The full per-schema account: every table, why it exists, and the constraints and anonymisation rules hanging off it. `CLAUDE.md` keeps the schema list, the cross-schema FK rules and the restore rule. Read this before adding a table, writing a migration, or changing anything about `catalog` / `app` / `import_ne`.

### Database topology

**One Postgres instance, three schemas.** It was four until NEU-1051 dropped `tvmaze` — the retired TV Maze mirror, whose 3.5M episodes, 484k people and 2.67M guest-cast rows went with it. The pre-drop `pg_dump` is the only copy; `scripts/dump_tvmaze.sh` takes and verifies it and `docs/migration/README.md` has the runbook.

- `catalog` — the source-neutral catalog mirror that replaces `tvmaze` (ADR-0007). Named for what it holds rather than where it came from, because the source has changed once already. **This is the read spine since NEU-1047** — every browse, search, `/me` and credits route reads it, and nothing in the running app reads `tvmaze` any more. `tvbf/tmdb/upsert.py` fills the tables (NEU-1033) and `POST /admin/catalog-ingest` is the pass that calls it over TMDB's whole catalog (NEU-1034). Spine: `show`, `season`, `episode`. Lookups + joins: `genre`, `network`, `production_company`, `keyword`, `watch_provider`, `country`, `language`, and one join table per relationship (`show_genre`, `show_network`, `season_network`, `show_production_company`, `show_origin_country`, `show_production_country`, `show_language`, `show_spoken_language`, `show_keyword`, `show_watch_provider`). Show-scoped detail: `content_rating`, `show_aka` (TMDB's `alternative_titles`, named for the glossary term), `translation`, `image`, `video`, `episode_group`, `show_creator` (the `created_by` show-creator credit, which TMDB models separately from crew and which carries no FK to `person`), `show_recommendation` (NEU-1052 — TMDB's "More like this" list as a show-to-show edge with a rank, 20 per source show; **no `source` column**, because one endpoint means one provenance, and ranks keep gaps where a target did not resolve rather than being renumbered), `trending_show` (NEU-1055 — the current `/trending/tv/week` list and nothing else: at most 20 rows keyed on `rank`, every one carrying the same `captured_at`, replaced whole in one transaction by the daily job. Not a history — a second snapshot would need a header table and nobody reads yesterday's. `captured_at` is stamped at the **fetch**, because NEU-1056's seven-day staleness cutoff is measured against it. Ranks keep gaps and `adult` / `deleted_upstream_at` are filtered at read time, both on `show_recommendation`'s reasoning). Credits (NEU-1038): `person`, `character`, `crew_role`, `show_cast`, `show_crew`, `episode_guest_cast`, `episode_crew` — all seven are **filled**, the first five from `aggregate_credits` by `tmdb/upsert.py:_write_credits` (NEU-1039), the two episode-grain ones from the season payload's `guest_stars` / `crew` by `_write_episode_credits` (NEU-1040). Plus `air_date_offset`, one integer per `(show_id, season_number)` recording how many days that season's mirrored dates are shifted from TMDB's (NEU-1145 — see the non-obvious patterns below), `airdate_show_state`, what the airdate pass knows about a show, keyed on `show_id` — the oracle's show id (`tvmaze_id` / `resolved_at`, NEU-1148: a pure derived cache, `DELETE` is always safe, and `tvmaze_id IS NULL` on a row means *asked, no counterpart* where no row means *never asked*) plus `last_reconciled_at` (NEU-1149), the nightly pass's own watermark, NULL meaning *never reconciled*. Two writers, never together: `show_state._record_link` owns the first pair, `show_state.mark_reconciled` the watermark — so the `DELETE` escape hatch now also clears every watermark and costs the next run a full-scope pass, `rate_budget`, the keyed request budget (a row per upstream source, NEU-1027), and `ingest_run`, which every run of every kind lives in — it moved here from `tvmaze` in NEU-1051 with `ALTER TABLE ... SET SCHEMA`, so every historical run row came with it and `ck_ingest_run_kind` still names the retired TV Maze kinds so those rows stay readable. Built to `docs/specs/NEU-1031-tmdb-coverage-audit.md`, which is the contract every column traces to; `tests/unit/catalog/test_audit_coverage.py` machine-checks that. Since **NEU-1146** the spine holds no `tmdb_id IS NULL` rows at all: ADR-0012 withdrew ADR-0008's locally-authored resting state, so an orphan in `show`, `season` or `episode` is now a defect to retire (`task retire:orphans`) rather than content held locally. It stays *representable* — `ON CONFLICT (tmdb_id)` still cannot match a NULL, which is what protects a row mid-flight — and a delta can create fresh ones, which is why the pass is re-runnable rather than one-shot. One column is not from the audit and traces to the migration instead: `show.match_method` (NEU-1043) records which mapping tier attached the row's `tmdb_id` — `tvdb_id` / `imdb_id` / `title_year`, guarded by `ck_show_match_method`, NULL when the migration did not map the row. A second is `show.tmdb_synced_at` (NEU-1034), the ingest's resumability watermark — see the non-obvious patterns below for why row-existence could not play that role. A third is `show.credits_synced_at` (NEU-1127), the credits backfill's watermark, which exists because the ingest ran before the credit writers merged and `tmdb_synced_at` cannot say so. A fourth is `show.recommendations_synced_at` (NEU-1052), the recommendations backfill's, for the same reason one column further along — the ingest ran before the namespace was appended at all. A fourth group is the four `tmdb_*` date columns — `episode.tmdb_air_date`, `season.tmdb_air_date`, `show.tmdb_first_air_date` / `tmdb_last_air_date` (NEU-1145) — which hold the *uncorrected* upstream value and are NULL for every row no correction was applied to, i.e. essentially all of them.
- `app` — user / auth / tracking / social data: `user` (which carries `disabled_at` since NEU-1162 — a nullable timestamp, **not a boolean**, because the question asked of a moderation action later is *when*, and it is the *only* record of the act: there is deliberately no `disabled_by` and no `disabled_reason`, since there is one admin and the grounds live in the report row and the Linear issue it created. Nothing cascades from it, no `ON DELETE` behaviour changes and no other row is touched — reversibility is the whole point against a `DELETE /me` that is not reversible; both columns are an additive migration later if moderation grows past one person), `session`, `auth_token` (its `payload` holds `{"new_email": ...}` for a pending email change, so `scripts/refresh_db.sh` truncates it during anonymisation for the reason it truncates `watch_archive` — NEU-1195), `login_attempt`, `auth_attempt` (NEU-1160 — one signup or failed-login attempt keyed on the client address, `(kind, ip, attempted_at)` with a checked two-value `kind`. **A new table rather than a widening of `login_attempt`**, which belongs to the email-keyed lockout and whose rows are cleared per-email on a successful login — the IP counter must deliberately never be. No FK to `app.user`: a signup attempt precedes the user and a throttled one has no user at all. Truncated by `scripts/refresh_db.sh`'s anonymisation, beside `login_attempt`, because it holds real addresses and a counter over a fifteen-minute window says nothing true once restored elsewhere), `invite`, `user_show_watch` (My Shows membership + added_at), `user_episode_watch` (per-episode watch records), `user_show_rating` / `user_episode_rating`, `connection` (friend graph; unordered-pair uniqueness with `requested` / `accepted` / `blocked` state), `activity_event`, `watch_archive` (the source-independent snapshot of every watch and rating — see below), `user_recommendation_set` / `user_recommendation` (NEU-1106 — one generated batch of weekly recommendations for one user and the resolved suggestions inside it; the set is superseded by a newer one, never mutated, which is what makes the swap atomic and non-destructive, and it doubles as the pass's run record, so there is no `ingest_run` row for that job; `compiled_payload` is a second copy of the user's watch history, so `scripts/refresh_db.sh` truncates the pair during anonymisation for the same reason it truncates `watch_archive`; `user_recommendation.recovered_from` (NEU-1173) holds the raw *dressed* title on the rare row the quoted-segment fallback recovered and NULL on every other, deliberately beside `matched_via` rather than inside it — that column answers which catalog tier matched and recovery is a property of the title, so one column carrying both facts is the shape that goes stale), `user_report` (NEU-1162 — one user's report of another: `reporter_id`, `reported_user_id`, `reason`, `created_at`, plus `ix_user_report_reporter_created`, which is exactly the query the throttle runs on every report. It is the ledger *and* the counter — every report is persisted anyway, so there is no `auth_attempt`-style side table and no "record the attempt" step to get wrong. **Both FKs cascade**, consistent with every other FK into `app.user`, and the consequence is stated rather than discovered: an abuser who self-deletes takes their reports with them, accepted because the Linear issue is the durable record — it holds the same reason text under a system with states and assignment. `RESTRICT` on `reported_user_id` was rejected outright, since it would let anyone block another person's account deletion by reporting them, which is a GDPR-shaped problem; `SET NULL` was rejected as leaving a row pointing at nobody. **No triage column**: Linear *is* the workflow, and a coarse copy of its state here would be a second record that immediately disagrees. Pruning is the same standing gap `auth_attempt` has, bounded by the throttle at 5 rows per reporter per day), `connection_request_log` (NEU-1157 — every connection request that was **created**, and how it ended: `requester_id`, `addressee_id`, `outcome`, `created_at`, `resolved_at`, plus `ix_connection_request_log_requester_created`, which is exactly the shape of both queries the throttle runs. It exists because `app.connection` **cannot** answer either of them: that row is deleted on both decline and cancel, through one code path that only `caller_id` distinguishes, so once a request resolves the database retains no evidence it existed — a cap counting `connection` rows is reset by cancelling, and the two outcomes the reputation rule most needs are exactly the ones erased. Making `app.connection` its own ledger, the `user_report` shape, was tried first and rejected: `uq_connection_unordered_pair` means a retained `declined` row 409s that pair *forever*, silently converting every decline into a permanent block. `outcome` is `Text` + `ck_connection_request_log_outcome` rather than a Postgres enum, unlike `connection.state`, following `auth_attempt` and for its reason — widening a check constraint is a loud migration where `ALTER TYPE ... ADD VALUE` slips through review, and a sixth outcome should be hard to add casually. **`addressee_id` is stored although no throttle arithmetic reads it** — every count is per-requester — because "who did this account spray, and how did each one go" is the question moderation asks and the one `app.connection` cannot answer once rows are deleted; the privacy cost is stated rather than discovered, since cancelling a request no longer erases the fact you asked. Both FKs cascade, making the retention sentence "for as long as both accounts exist", and the accepted cost is that a target who deletes their account takes the record of their decline with them. **Not truncated by `scripts/refresh_db.sh`'s anonymisation** — the row is ids and timestamps and nothing more, the same class as `user_recommendation_dismissal`. Not pruned either, and deliberately: a pruning job would be a fifth Coolify scheduled task with its own deadman for a few thousand rows nobody reads, and this table is moderation evidence, so a griefer's history auto-erasing on a 30-day timer is precisely the wrong property), `user_recommendation_dismissal` (NEU-1178 — one show one user has removed from their recommendations for good, `(user_id, show_id)` composite PK on `user_show_watch`'s shape because the pair *is* the fact and it doubles as `ON CONFLICT DO NOTHING`'s index target; no standalone index on `show_id` for that table's reason, and **not** truncated by `scripts/refresh_db.sh`'s anonymisation, because the row is `(user_id, show_id, created_at)` and nothing more — the same class as `user_show_watch`, unlike the recommendation-set pair whose `compiled_payload` is a second copy of the watch history). One Alembic version table (`app.alembic_version`) — migrations live in `migrations/versions/` (the Alembic env is `migrations/`, configured by `alembic.ini`).
- `import_ne` — staging tables for the one-off Next Episode data import (`series`, `episode_mark`, `show_candidate`, `show_match`, `show_resolution`, ...). Not part of the running app; kept for re-runs and auditing.

Cross-schema foreign keys are intentional and used, and since NEU-1046 they point at **`catalog`**, not `tvmaze`: `app.user_show_watch.show_id`, `app.user_show_rating.show_id`, `app.user_recommendation.show_id` (NEU-1106) and `import_ne.show_resolution.show_id` reference `catalog.show.id`; `app.user_episode_watch.episode_id` and `app.user_episode_rating.episode_id` reference `catalog.episode.id`. All with full referential integrity, and each `ON DELETE` behaviour carried across verbatim — the `app` ones all CASCADE, the `import_ne` one is NO ACTION. That was a constraint swap and not a data migration: no `app` row's values changed, because NEU-1042 preserved TV Maze's ids as the catalog surrogates. `app.activity_event` is polymorphic with no FK at all and so had nothing to repoint, which is why the reconciliation harness counts its rows explicitly.

The corollary is that **nothing in `app` referenced `tvmaze`**, which is the property that let NEU-1051 drop it: the `CASCADE` had no inbound constraint to follow. `test_watch_rows_hang_off_catalog_and_cascade_from_it` in `tests/integration/app/test_models.py` is what still proves the positive half; its `test_dropping_the_tvmaze_row_no_longer_touches_user_data` twin went with the schema, having no subject left.

Because `app` tables are built by `create_all` in the test suite and by Alembic in prod, every one of these constraints is **named explicitly in `app/models.py`** so the two agree. Test fixtures need `tests/fixtures/spines.py`, which since NEU-1051 holds only `without_catalog_fk(session, table)` — it stands one constraint down for a block, needed by the handful of tests that reconstruct the *pre-repoint* state the unmirrored-row reports exist to find. Its `mirror_spine` sibling went with the schema it mirrored from; tests seed `catalog` directly now.

**Anything that drops and restores the `catalog` schema must restore these FKs.** `DROP SCHEMA ... CASCADE` removes them silently, and constraints defined on tables outside the restored set do not come back with a `pg_dump --schema=catalog`. `scripts/refresh_db.sh` handles this by snapshotting `pg_get_constraintdef` for every FK pointing into the restored schemas from outside them, then replaying it after `pg_restore` — don't replace that with a hardcoded list, which is exactly how the ratings and `import_ne` constraints got silently dropped.
