# TVBF: Personalized Recommendations — project spec

**Status:** approved 2026-08-10
**Blocked by:** [TVBF: TMDB Migration](tvbf-tmdb-migration-project-spec.md) — cutover
**Related:** [TVBF: TMDB Discovery](tvbf-tmdb-discovery-project-spec.md) — owns trending / most
anticipated / similar shows; this project owns everything derived from the user's own data.
**Decision record:** ADR-0002 (no upstream API in the request path), ADR-0008 (user data
references internal ids), ADR-0013 (recommendations are generated from watch behaviour —
written by NEU-1101; the spec drafted it as ADR-0009, a number the TMDB migration took first).

## 1. Purpose

Weekly, per-user show recommendations generated by an LLM from **the requesting user's own
watch behaviour and nothing else** — My Shows membership, per-episode completion, and star
ratings — surfaced on a new `/discover` page as "Recommended for you".

## 2. Why an LLM, and why not collaborative filtering

TMDB Discovery's spec hands "people who watched this also watched" to this project. That
signal is not buildable here and will not be: production has **5 users**. A co-watching
matrix over five people and 563 distinct shows is noise, and no amount of tuning fixes a
sample-size problem.

What the feature actually requires is a bridge from *what this person watched* to *what
exists that they haven't seen* — which is world knowledge, not a statistic we hold. An LLM
is the only component available that has it. This is a **generation** task with a
**resolution** step, not a ranking task over a candidate set.

Two consequences follow and are load-bearing throughout:

- **No other user's data enters a prompt, ever.** Feeding user B's history into a request
  that produces recommendations for user A leaks B's viewing to a third party for no
  measurable gain at this scale. Friend-derived signals are out of scope (§13).
- **The model's taste *is* the product.** There is no ranking layer, no feedback loop, and
  no post-processing that rescues a weak suggestion. Everything downstream of the response
  is resolution and filtering.

## 3. Scope

**In scope:** the taste payload, the provider client, the weekly pass, resolution to
`catalog.show`, storage, a read endpoint, and the `/discover` page shell plus its
"Recommended for you" section.

**Out of scope** (see §13 for the full list with reasoning): dismissal / negative feedback,
friend-derived signals, trending / most anticipated / similar shows (TMDB Discovery),
per-show "because you watched X" causal attribution.

**This project creates the `/discover` page.** TMDB Discovery defines three surfaces but
never specifies where trending and most anticipated live, and the route does not exist
today. Waiting for Discovery to claim it yields no page — Discovery is itself blocked on
the migration. The page contract is therefore owned here and published to
`tvbf-backend/docs/specs/` so Discovery's tickets, and the frontend repo, can cite it by
URL (CLAUDE.md's cross-repo-citation rule).

## 4. Measured baseline (2026-08-10)

Local `app` data, which is a refresh of production and matches the migration spec's
production figures (563 distinct shows touched, 199 with episode watches).

| | |
|---|---|
| Users | 3 (production: 5) |
| My Shows rows | 577 — per user: 522 / 50 / 5 |
| **My Shows rows with zero watched episodes** | **369 (64%)** |
| (user, show) pairs with ≥1 episode watch | 216 |
| **Watched but not in My Shows** | **8** |
| Show ratings / episode ratings | 3 / 1 locally; 61 / 76 in production |
| `watched_at` range | 1994-09-22 → 2026-08-03 |

Three of these drive design decisions directly:

- **64% of My Shows has no watches.** My Shows is a watchlist as much as a library, so
  "in My Shows" cannot mean "liked" — that would make two thirds of the positive signal
  aspirational (§5.1).
- **Only 8 rows are watched-but-not-added.** The abandonment signal is nearly empty in
  practice, so the design must not depend on it.
- **`watched_at` spans three decades**, backfilled by the Next Episode import. Recency and
  abandonment are genuinely computable, not guesses.

## 5. The taste payload

### 5.1 Classification

Three tiers. **Ratings outrank completion; completion outranks membership.**

**Rating override** — applied first, when a rating is available:

| Rating | Result |
|---|---|
| ≥ 3.5★ | LIKED regardless of completion |
| ≤ 2.0★ | NOT LIKED regardless of completion |
| 2.5–3.0★ | No override — falls through to behaviour |

Ratings are `Numeric(2,1)` constrained to half-stars 0.5–5.0 by
`ck_user_show_rating_stars` — **ten values, not the 1–5 integers the original stub
assumed.** The dead band is deliberate: a 3★ means "it was fine", and completion measures
"fine" better than a star does. Overriding on it would invent a signal the user did not
send, and would let a lukewarm rating flip a show the user actually finished out of LIKED.

**Which rating.** A show rating wins outright. Absent one, synthesize from the mean of
*that user's* episode ratings for that show. Episode ratings are never used when a show
rating exists.

**Behavioural tiers** — applied when no rating override fires:

| Tier | Rule |
|---|---|
| **LIKED** | ≥ 50% complete (in My Shows or not), or in My Shows with ≥ 1 episode watched |
| **NOT LIKED** | ≥ 1 episode watched, < 50% complete, **and** nothing watched in 180 days |
| **INTERESTED** | In My Shows, zero episodes watched |

The 180-day clause on NOT LIKED is what separates *abandoned* from *just started*. Without
it a show begun last week is indistinguishable from one bailed on in 2019, and the data
supports the distinction.

INTERESTED exists so the 369 never-started rows are neither discarded (losing real
information — someone who watchlists ten Scandinavian crime dramas has told you something)
nor labelled LIKED (overstating it). It costs one enum value.

### 5.2 Completion percentage

`episodes_watched / aired_episodes`, **not total episodes**. Against the total, a
currently-airing show that the user is fully caught up on reads as ~85% and can never reach
100%, so "caught up" and "finished" must both land at 100% or the tiers misclassify every
ongoing series.

### 5.3 Payload shape

Columnar JSON, grouped by label, with a single column header:

```json
{"columns": ["title", "year", "pct", "stars"],
 "liked":      [["Game of Thrones", 2011, 100, 4.5], ["Shogun", 2024, 100, null]],
 "not_liked":  [["Emily in Paris", 2020, 12, null]],
 "interested": [["Dark", 2017, 0, null]]}
```

Costed against the heaviest real account (522 shows): ~9 tokens per row versus ~38 for
repeated-key JSON objects with a per-row label — 4.7k tokens versus 20k. Grouping makes the
label free rather than ~3 tokens per row; the header declares the schema once rather than
522 times.

**`tmdb_id` is deliberately absent.** Recommendations are by definition shows *not* in the
input, so the model can never echo an id back, and a numeric identifier contributes nothing
to taste inference. We build the payload, so we already know every id. It is ~2k tokens per
call for a field with no consumer on either side — and the original stub's own constraints
section warned against it ("Do not feed raw numeric TMDB IDs into the LLM as inputs").
**Premiere year, not full date**, for the same reason: the year disambiguates a title; the
month and day are three tokens no reasoning step touches.

**`interested` is capped at the 50 most recently added.** Its signal is weakest per item
and it is the tier most likely to dominate the payload by volume.

#### Amendment, 2026-08-17 — the `exclude` group (`PROMPT_VERSION` 3)

The shape above is missing a fourth group and shipped that way for two versions:

```json
{"columns": ["title", "year", "pct", "stars"],
 "exclude_columns": ["title", "year"],
 "liked": [...], "not_liked": [...], "interested": [...],
 "exclude": [["Slow Horses", 2022]]}
```

`exclude` names every show §8's filter would drop that **no tier group mentions** — the
`interested` cap's overflow, a show carrying only an episode rating, a show no §5.1 tier
covers. Title and year only, because such a show reached no tier and there is no `pct` or
`stars` to report.

It exists because the sentence above — "recommendations are by definition shows *not* in the
input" — described an intent rather than a mechanism. §8's exclusion set has always been
wider than the payload's rows, so the model was asked to avoid shows it was never shown. On
2026-08-17 at 16:00 UTC a production run returned 25 well-formed bare titles of which **25 of
25** were already in its own input, stored none of them, and recorded `no_matches` while the
previous set stayed on the page. The instruction now names all four groups and says what to
do instead of naming an excluded show; the pass additionally retries once when more than nine
tenths of an answer is the user's own library (`IGNORED_EXCLUSION_FRACTION`).

Token cost is the size of that overflow — a title/year pair is ~10 tokens, and for the
account this was diagnosed on the group holds 4 entries against 95 tier rows. A user with a
few hundred capped `interested` shows pays a few thousand tokens for it, which is the price
of an instruction that can be followed.

Honest sizing: at DeepSeek rates the compact-versus-verbose difference is ~$0.0014 per
call — roughly $70/year apart even at a thousand weekly users. The compact form is chosen
for **context headroom** (a 2,000-show account is 18k tokens compact, 76k verbose) and
signal-to-noise, not for the dollars.

### 5.4 Generation floor

```
(2 × liked_count) + interested_count >= 10
```

One expression, one generation path. It reproduces both intuitive endpoints exactly — 5
LIKED alone qualifies, 10 INTERESTED alone qualifies — and covers the mixed middle that two
independent thresholds would refuse: 3 LIKED + 4 INTERESTED qualifies, as it should.

The 2:1 weighting states the belief plainly — **a show you watched tells us about twice
what a show you bookmarked does** — and is a named constant, because it is the first thing
you will want to change when evaluating whether cold-start sets are worse than established
ones.

**NOT LIKED contributes nothing to the floor.** It is exclusion signal; you cannot generate
from a list of things someone disliked.

Below the floor: write a set row with `status = 'insufficient_history'`, the payload hash,
and no recommendation rows. This composes with the hash gate for free — the user is skipped
at zero cost every week until their payload changes, and qualifies automatically on the next
run after it does. No timer, no separate bookkeeping.

**Accepted trade:** a user whose entire history is INTERESTED generates from pure intent
with **no negative signal at all**. Those sets will be measurably weaker. The generous floor
is still right — it gets people into the feature — but the framing is "weaker, knowingly",
not "equivalent". The stored payload and raw response (§8) are what let this be checked
later rather than assumed.

## 6. The provider client

**DeepSeek via DeepInfra**, OpenAI-compatible endpoint, `Authorization: Bearer`. Chosen for
per-user cost scaling: the workload is one call per changed user per week, and cost must
stay flat as accounts are added rather than tracking a frontier-model tier.

**Ported from `upcoming-movies-backend/src/upmovies/llm/`**, trimmed. That package is a
mature 1,296-line provider-neutral gateway with its own ADR trail; the parts that transfer
are the provider-neutral prompt type, `openai_compat`, and `retry`. The parts that do not:
`pricing`, `offline`, the four-stage configuration validation, and the byte-identical-prefix
caching contract — all earned by upmovies' four stages across three providers, and inert for
one stage at this volume.

**The copy is deliberate and its cost is accepted**: the two codebases will drift and a fix
in one will not reach the other. A shared package is the textbook answer and the wrong one
here — two personal repos, no shared publishing setup, and it would couple TVBF's release
cadence to upmovies'. If a third consumer appears, *that* is when extraction pays.

**Base URLs are constants in the registry, not settings.** upmovies' `registry.py` argues
this correctly: a base URL is a property of the provider, not of a deployment, and making it
configurable adds an env var whose only correct value is the one in the source, plus a
second one to get wrong. The **model id is** a setting — that is the knob that gets turned.

### 6.1 Rate budget

DeepInfra becomes a keyed source in the existing cross-process budget (NEU-1027): a row in
`catalog.rate_budget` and a `BUCKETS` entry, reached through
`get_rate_limiter(source, Budget(...))`.

At five weekly calls this is unnecessary today. It is three lines, and CLAUDE.md records
that this codebase has twice shipped a bare per-process limiter and twice paid for the
doubled rate (NEU-955, then ADR-0006). It is also what makes the eventual concurrency
change (§9) safe rather than dangerous. Pass a `Budget` dataclass, never loose arguments —
`get_rate_limiter` is `@cache`d on the literal call.

### 6.2 Provider constraint — measured, not assumed

`upmovies/llm/types.py` records that **DeepSeek rejects the request with a 400 unless the
word "json" appears somewhere in the prompt** when `response_format` is set. This is a hard
failure on the chosen provider. The system prompt must contain the literal word, and the
constraint needs a comment at the site so nobody "cleans up" the wording later.

**Re-measured 2026-08-15 (NEU-1100, `scripts/probe_deepinfra.py`) and it did not
reproduce.** On both `deepseek-ai/DeepSeek-V4-Pro-0813` and `deepseek-ai/DeepSeek-V4-Flash`,
`response_format` with the word absent entirely, present only in uppercase, and present only
in the user message each answered 200 with a decodable JSON object. The requirement is
enforced in `client._to_wire` anyway: the evidence is two ids on one day out of a catalog of
nine that rotates, a refusal costs one word and is raised before anything is sent, and the
400 it stands in front of is non-retryable and costs a user their week. The paragraph above
is what the enforcement is now *knowingly* stricter than.

## 7. The model request and its output

**Request 25 recommendations, display 12.** The headroom absorbs resolution failures, the
never-recommend filter, and read-time tombstone/adult filtering — the same reasoning
TMDB Discovery's spec uses for storing 20 and showing 12.

**Output contract:**

```json
{"recommendations": [{"title": "...", "release_year": 2019, "reason": "one sentence"}]}
```

**`release_year` is required, and a recommendation arriving without it is dropped.** It is
the only disambiguator resolution has; without it step 1 of §8 is unbounded. This does
occasionally discard a valid suggestion, which is the accepted cost.

**`reason` is the first LLM-authored prose TVBF shows users.** It renders as plain text,
never markup. It can assert things about a show that are untrue, and can describe a show
subtly different from the one resolution landed on.

## 8. Resolution

Model-authored `title` + `release_year` → `catalog.show.id`. **Entirely local — no upstream
call**, so ADR-0002 holds without exception and resolution costs nothing per recommendation.
The indexes already exist (migration `aa4571de8f17`): `ix_show_name_folded_trgm` on
`catalog.show`, `ix_show_aka_title_folded_trgm` on `catalog.show_aka`.

1. Fold-exact on `catalog.show.name`, year within ±1
2. Failing that, fold-exact on `catalog.show_aka.title`, year within ±1
3. Failing that, **drop and log the raw title**

Folding uses `tvbf.sql_fold` — `folded()` / `folded_equal()`, evaluated in Postgres. There
is exactly one fold and it is not reproducible in Python (`unicodedata` does not decompose
ł, ø, đ, ħ). Do not write a second one.

The AKA step earns its place: a model recommending international television names shows in
English, and `catalog.show_aka` holds TMDB's `alternative_titles`. That is the step that
catches "Money Heist" for *La casa de papel*.

**No fuzzy / trigram fallback. This is the most important negative decision in the project.**
A similarity threshold solves a *human search box* problem — typos — that does not exist
here. An LLM naming television series either knows the show or invented one, so a threshold
buys almost no true matches while converting every hallucination into a confident wrong
match, and introduces a magic number nobody can calibrate. **A resolution failure is a
useful signal, not a defect to paper over**: an unmatched title is either a hallucination or
a genuine catalog gap, and both belong in the logs rather than silently mapped onto whatever
scored 0.7.

**Ambiguity resolves by `popularity`, not to unmatched.** When two rows fold-equal at the
same year (reboots, remakes), take the higher `popularity`. This deliberately **diverges
from NEU-1043**, where every ambiguity resolves to unmatched — there a false positive
silently attached a user's watch history to the wrong show and was unrecoverable; here it
shows a less-likely card in a grid of twelve. The costs are not comparable, and the rules
should not be either.

**Exclusions.** Never recommend any show the user has a record for — the union of My Shows,
any episode watch, any show rating, any episode rating. Usefully this is the same set the
payload is built from, so **the payload is the exclusion list** and no second query is
needed. Enforcement is belt-and-braces: the prompt states it (the model has the list), and a
post-resolution filter guarantees it.

`adult` and `deleted_upstream_at` are filtered **at read time**, not only at write time — a
set generated in March can contain a show tombstoned in June. This is what the 25/12
headroom is for.

## 9. Storage

**`app.user_recommendation_set`** — one row per generated set:
`id`, `user_id` (FK → `app.user`, CASCADE), `generated_at`, `payload_hash`, `prompt_version`,
`model`, `status`, `input_tokens`, `output_tokens`, `compiled_payload` (JSONB),
`raw_response` (JSONB).

**`app.user_recommendation`** — one row per suggestion:
`set_id` (FK, CASCADE), `rank`, `show_id` (FK → `catalog.show.id`, CASCADE), `reason`,
`matched_via`.

**Reads take the newest row per user where `status = 'succeeded'`.**

`status` ∈ `succeeded` | `failed` | `no_matches` | `insufficient_history`.

What each piece buys:

- **The set row makes the swap atomic and non-destructive.** Insert the new set and its
  rows; the previous set simply stops being newest. No `DELETE` before a write that might
  fail, and a provider outage leaves last week's recommendations standing rather than
  blanking the section. This is the single most important property here — the alternative
  failure mode is a user opening the app to an empty page because the provider 503'd at 4am.
- **`status` separates three states that look identical from outside**: never ran, ran and
  resolved nothing, ran and failed. At 3–5 users nobody will file a bug, so the table is the
  only place failure becomes visible.
- **`input_tokens` / `output_tokens` / `model` per run is the scaling instrument.** Cost
  recorded at the point of spend is what makes "does this scale" answerable, and what makes
  a prompt change evaluable across `prompt_version` values instead of guessed at.
- **`compiled_payload` + `raw_response` are how a bad recommendation gets diagnosed** — what
  the model was told *and* what it said. ~12KB for the heaviest user, ~260 rows/year; no
  pruning needed. Note this puts a copy of the user's watch history in a second place; the
  `user_id` CASCADE is what keeps account deletion complete, unlike `watch_archive`, which
  deliberately has no FK at all.
- **`matched_via`** (`name` / `aka`) ports NEU-1043's `match_method` for the same reason it
  exists there: it makes one resolution tier retractable as a batch — a `WHERE` clause
  rather than a re-run of every user.

**First `app` → `catalog` foreign key.** Everything in `app` currently references `tvmaze`.
This is correct and forward-looking, but it means `scripts/refresh_db.sh` snapshots an
inbound FK on `catalog` for the first time. CLAUDE.md is explicit that exactly this
mechanism silently dropped the ratings and `import_ne` constraints once already — **verify
with a real refresh, do not assume.**

### 9.1 The regeneration gate

Hash the canonical serialization of the compiled payload, plus `prompt_version` and the
model id. Compare against the hash on the user's current set. Identical → skip; different →
call.

**A timestamp watermark cannot work here.** `activity_event` rows are deleted on unwatch
(`activity_event_repo.py:62-92`), and every other candidate timestamp (`added_at`,
`watched_at`, `rated_at`) lives on rows that get deleted too. **No max-timestamp watermark
can see a deletion** — a user who unwatches a season, removes shows, or deletes a rating
looks unchanged, and keeps recommendations reflecting a taste profile they have revised.

The hash is provably correct rather than approximately correct: the payload *is* the model's
entire input, so identical bytes mean identical output. It costs a query, not a call — and
the call is the expensive part, so it saves 100% of the spend it targets.

**The strongest argument is product, not cost.** A user who changed nothing must not see
their recommendations churn week to week; that reads as randomness and undermines the whole
surface. A timestamp cannot deliver that — unwatch-then-rewatch yields a fresh timestamp
with identical state.

**`prompt_version` and model id are in the hash input** because otherwise editing the prompt
changes what the pass *would* produce while every hash still matches, and nobody ever
regenerates. Shipping a prompt change re-runs everyone exactly once, which is also the only
way to evaluate it against real users.

**No maximum staleness.** An unchanged user keeps their set indefinitely. Regenerating on a
timer is precisely the churn the hash exists to prevent, and the model recommends from its
own world knowledge rather than from our catalog, so catalog growth does not change output.

## 10. The weekly pass

`python -m tvbf.jobs.weekly_recommendations`, a **Coolify scheduled task running Sundays**,
following NEU-1008: the process is the run, the exit code is the result,
`configure_logging()` in `main()`, and a healthchecks.io deadman catches the task never
firing at all.

**No `ingest_run` row, and no run table of any kind.** CLAUDE.md's NEU-1034 note reasons
that a second home for run rows means a second stale-run cleanup, a second liveness guard,
and a second status route. That applies with more force here: `user_recommendation_set`
already *is* a per-user run record carrying status, timing, tokens, and the raw response. A
run row would duplicate it at a coarser grain for a job that finishes in seconds.

**`pg_try_advisory_lock` replaces `_reject_if_in_flight`.** Dropping the run table drops
that guard, and it was doing real work — a manual trigger during the cron would have both
processes read the same stale hash, both find the user dirty, and both spend a call. One
statement, no table, no staleness heuristic, and it releases automatically when the
connection dies, which is exactly the failure mode `INGEST_STALE_RUN_MINUTES` exists to
paper over for long-running jobs. A second process finding the lock held logs and exits 0.

**Sequential per user, with a named threshold for changing it.** At 3–5 users the pass is
~30 seconds and concurrency would be pure complexity. Sequential cost is `users × latency`,
so this stops being right somewhere around **100–200 users**; the fix then is a bounded
semaphore, not a rewrite. Writing the threshold down beats pre-building for it.

### 10.1 Failure semantics

- **Per-user failures are isolated** — write `status = 'failed'`, log, continue. Five users
  must not lose recommendations because the first hit a 429.
- **Abort after 3 consecutive failures** (hardcoded constant, not an env var — a setting
  implies a tuning need that will not materialize at this scale, and every setting is a
  thing to get wrong). Same shape as the ingest's consecutive-failure threshold.
- **Exit 1 if any user failed.** At 3–5 accounts one failure is 20–33% of the user base, and
  the client's retry/backoff has already absorbed anything transient — so a failure that
  survives retry is worth waking up for. Coolify notifies on failure.
- **One retry on malformed or unparseable JSON**, against the same payload. LLM JSON
  failures are frequently one-off and a second call costs a fraction of a cent. A second
  failure writes `status = 'failed'`.
- **Resolution failures are not run failures.** 25 titles returning 19 matches is a success
  with 19 rows — exactly as NEU-1043 treats unmatched shows as expected output. Unmatched
  titles are logged and preserved in `raw_response`.
- **Zero resolved titles is `no_matches`, not `succeeded`.** Because reads take the newest
  `succeeded` set, this leaves last week's recommendations standing instead of silently
  emptying the section, and makes a systematic resolution break visible rather than looking
  like a quiet week.

### 10.2 `--dry-run`

`python -m tvbf.jobs.weekly_recommendations --dry-run --user <id>` compiles and prints the
exact payload plus its token count, and exits without calling. ~10 lines, following
`tmdb_enrichment`'s `-- --limit N` precedent.

This is how the classification rules get verified. Every rule in §5 — the tier boundaries,
the rating overrides, the 180-day clause, the 50-cap, the weighted floor — was chosen from
aggregate counts. `--dry-run` against the real 522-show account is what turns them from
plausible into checked, before any of it reaches a model.

**CLI-only, deliberately no admin endpoint.** The payload is a user's complete watch
history; exposing it over HTTP, even behind the admin token, creates a data-egress surface
for something whose only consumer is a terminal.

## 11. API and frontend

**`GET /me/recommendations`** — `get_current_user`, returns up to 12 resolved
recommendations from the newest `succeeded` set, filtered for `adult` and
`deleted_upstream_at` at read time. `Cache-Control: no-store`, matching the existing `/me`
convention (`routers/me.py:542`).

**`POST /admin/recommendations`** — bearer `ADMIN_TOKEN`, optional `user_id` body field,
`202 + run_id`, background task. Regenerating a single account after a prompt change without
waiting for Sunday is the reason this exists.

**`/discover`** — new route, **fifth nav item** in `AppShell`, section heading
**"Recommended for you"**.

- `ShowGrid`, 12 cards: poster, title, year, and `reason` as one line of body text.
- **No sort control, no filters, no pagination.** The ranking is the model's, and letting
  users re-sort discards the only ordering that carries information. No `usePersistedSort`
  module — this stays the smallest frontend ticket in the project.
- **No rows → no section**, following Discovery's rule exactly. No empty state, no
  "add more shows" nudge, no spinner, no error. Discovery's spec argues an unclickable card
  costs a real moment of "why is this broken?"; an empty-state panel explaining an absent
  feature costs the same thing more slowly while advertising machinery nobody asked about.
- **"Recommended for you", not "Because you watched"** — the latter promises a per-show
  causal link the `reason` does not deliver, since the model reasons over the whole profile.
- **No AI-generated label** (decided).

**Why not Watch Next:** Watch Next is the index route and its contract is precisely "shows
you track with unwatched episodes". A recommendation for an untracked show has no business
there, and that page's clarity is worth more than the nav slot a tab would save.

**Cost accepted:** five items in the mobile nav. `AppShell` threads a `placement` prop with
`showLabel(placement)`, i.e. an icon-only bottom bar on small screens — five is workable and
is the practical ceiling. Discovery's surfaces add no further items, since they share this
page.

## 12. Testing

- **Pure unit tests** for classification, the floor, capping, payload serialization, and
  hashing — no DB. `tests/conftest.py:125-138` already swaps `rate_budget.build_limiter`
  suite-wide, so the DeepInfra budget needs no database either.
- **DB-backed integration tests** for resolution against seeded `catalog.show` +
  `catalog.show_aka`, following `tests/integration/tmdb/test_enrichment.py`.
- **`respx`** (already a dev dependency) for the client. **No test ever calls DeepInfra.**
- **Recorded real responses committed as fixtures** — at least three: one clean, one with a
  title that will not resolve, one malformed. Hand-written fixtures encode what we *think*
  the model returns; the failure modes that matter are the ones we would not think to write.

**Known constraint:** `catalog` is not read from until cutover and may be sparsely populated
locally while the TMDB ingest runs, so resolution tests seed their own fixtures rather than
relying on ambient catalog data.

## 13. Out of scope, with reasons

- **Dismissal / "not interested"** — needs a new table, feeds back into the prompt as
  negative signal, and changes the payload hash. A real feature, deferred until there is
  evidence the recommendations are good enough that dismissing is the main thing users want
  to do with them.
- **Friend-derived signals** ("trending among your connections") — a privacy question, not
  just a scope one: another user's history would enter a third-party prompt.
- **Episode ratings as an independent signal** — used only to synthesize a missing show
  rating (§5.1). Aggregating 76 rows across a handful of shows into a taste input muddies
  more than it adds.
- **Trending, most anticipated, similar shows** — TMDB Discovery owns all three.
- **Per-show causal attribution** — the model reasons over the whole profile; claiming
  "because you watched X" would be a fabrication.
- **A response cache of any kind.** ADR-0002 applies without exception; the stored set *is*
  the precomputed result.

## 14. Decision record and glossary to land

**ADR-0013 — "Recommendations are generated from watch behaviour"** (drafted here as ADR-0009;
0009–0012 were taken by the TMDB migration before this project started), written into
`tvbf-backend/docs/adr/` by the first milestone's ticket. It records: that this is an LLM
generation task rather than collaborative filtering, with the n=5 reasoning; that the
provider is chosen for per-user cost scaling rather than model tier; and that resolution is
local-only so ADR-0002 holds without exception.

**Four `CONTEXT.md` glossary entries:**

- **Recommendation set** — one generated batch for one user; superseded by a newer set,
  never mutated. _Avoid_: cache, prediction, batch.
- **Taste signal** — a show's LIKED / NOT LIKED / INTERESTED classification for one user,
  derived from rating, completion and membership in that order. _Avoid_: score, weight.
- **Taste payload** — the compiled columnar JSON sent to the model. It is simultaneously the
  model's input, the hash input, and the exclusion list; one object, three jobs.
- **Resolution** — turning a model-authored title + year into a `catalog.show` surrogate id.
  _Avoid_: matching, which collides with NEU-1043's `match_method`.

## 15. Milestone shape

Refined in the Linear project. The natural sequence:

1. **Client and budget** — trimmed `tvbf/llm/`, DeepInfra bucket, config, `respx` tests.

   `--dry-run`.

4. **The weekly pass** — job entrypoint, advisory lock, failure semantics, admin trigger,
   Coolify task, deadman.
