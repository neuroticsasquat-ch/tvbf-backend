# TVBF: TMDB Migration — project spec

**Status:** approved 2026-08-08
**Decision record:** [ADR-0007](../adr/0007-tmdb-replaces-tvmaze-as-the-catalog-source.md), [ADR-0008](../adr/0008-user-data-references-internal-ids.md)
**Blocks:** [TVBF: TMDB Discovery](tvbf-tmdb-discovery-project-spec.md)

## Purpose

Replace TV Maze with TMDB as TVBF's catalog source, migrate all user data onto the new
spine without losing a single record, and retire the `tvmaze` schema.

## The hard constraint

**No user loses a tracked show, a watched episode, or a rating. Period.** This holds even
where TMDB has no counterpart for the show or episode in question, and human matching is
an acceptable cost to uphold it.

Every design decision below that looks like over-engineering is traceable to this line.

## Architecture

### Schema and keys

A new **`catalog`** schema, named for what it holds rather than where it came from.
Adding it touches four places that enumerate schemas by hand — `migrations/env.py:25`,
`Taskfile.yml:51`, `tests/conftest.py` (lines 33-36, 52, 143), and CLAUDE.md's DB-topology
section.

`catalog.show.id` and `catalog.episode.id` are **generated identities**; `tmdb_id` is a
unique natural key that upserts conflict-target on (ADR-0008). `app.*` references
surrogates. `tmdb_id IS NULL` denotes a **locally-authored row** — permanent, never
deleted or overwritten by ingest.

`scripts/refresh_db.sh` snapshots inbound FK definitions generically, so it *should* cover
`catalog` automatically. That must be **verified with a real refresh**, not assumed —
CLAUDE.md records that exactly this mechanism silently dropped the ratings and `import_ne`
constraints once already.

### TMDB client

- Auth via **v4 read access token** as `Authorization: Bearer`, not the v3 `api_key` query
  parameter, which leaks into access logs and error reports.
- Config: `TMDB_READ_ACCESS_TOKEN`, `TMDB_BASE_URL`, `TMDB_IMAGE_BASE_URL`,
  `TMDB_RATE_LIMIT_*`. Server-side only; nothing TMDB-shaped reaches the SPA.
- **Rate: 20 req/s by default**, against a documented ceiling of ~40–50/s with 20
  connections per IP. Half the ceiling, still 11× TV Maze, and no deadline needs more.
- `append_to_response` returns the show plus `external_ids`, `alternative_titles`,
  `aggregate_credits` and individual seasons with full episode lists in one request.
  The documented limit is 20 appended items — **verify this as an acceptance criterion**;
  long-running shows need follow-up requests.

### Request budget

`DatabaseRateLimiter` (ADR-0006) generalises: parameterise the table and row instead of
the hardcoded `_ROW_ID = 1`, add a second one-row bucket for TMDB, and move the module out
of `tvbf/tvmaze/` to a neutral home. TV Maze's bucket and its calibration are untouched.

**Add block leasing — `acquire(n)`.** At TV Maze's 1.8 req/s a locked round trip per
request is free; at 20–40 req/s it is 20–40 serialised transactions per second through a
single row, roughly 20× the pressure the design was validated at. Leasing ~25 tokens per
locked transaction cuts lock traffic to ~1/s while preserving the cross-process guarantee,
because the block is deducted atomically before any of it is spent. A process dying
mid-lease forfeits unspent tokens, which errs slow — the direction `rate_budget.py:104-106`
already deliberately errs.

Two TMDB processes will exist (scheduled jobs and in-app admin passes), which is the
NEU-1008 shape. An in-process limiter would re-introduce rate doubling for the third time.

### Ingest

**Full list:** the daily id export,
`https://files.tmdb.org/p/exports/tv_series_ids_MM_DD_YYYY.json.gz` — one JSON object per
line, includes `popularity`, regenerated by 08:00 UTC, retained three months. A single
static file download, no pagination, no rate-limit spend. This is the authoritative
full-catalog list and plays the role `/updates/shows` played for TV Maze.

**Delta:** `/tv/changes`, 14-day maximum window, 100 per page, returning `id` + `adult`.
Cursor semantics differ from TV Maze — a date range rather than a per-show epoch — so
`last_update_cursor` changes meaning.

**Tombstones:** ADR-0005 ports unchanged, including the floor guards. A truncated or empty
export would otherwise tombstone the entire catalog; `_MIN_FEED_ABSOLUTE` and
`_MIN_FEED_RELATIVE` are recalibrated against 228,611 rather than 89k. Locally-authored
rows are exempt from tombstoning by definition — they were never in the feed.

**Season pruning:** ADR-0004's rule ports — the payload is authoritative for the season
set when seasons were requested, and the prune stays *between* the season upsert and the
episode upsert.

### Credits

TMDB's `aggregate_credits` returns cast with `roles: [{credit_id, character, episode_count}]`.
There is no character entity.

**Intern character per show** — `catalog.character(show_id, name)` — the same pattern
`crew_role` already uses. Preserves recasting and voice ensembles (2,621 characters in
prod), loses cross-show identity (1 character in prod). `episode_count` per role is
strictly better than the billing-order proxy we have today.

## Migration

### 1. The archive comes first

Before any TMDB catalog work: snapshot every watch and rating record into a
**source-independent archive** — user, show name, premiere year, season number, episode
number, episode title, airdate, watched-at, plus the TV Maze/IMDb/TVDB ids as they stand
today. Immutable, never dropped, survives `DROP SCHEMA tvmaze`.

This decouples the no-loss guarantee from the migration's success. A catastrophic mapping
failure remains recoverable by hand indefinitely, because the archive describes what was
watched in human terms rather than by a foreign key.

### 2. Mapping is transitional scaffolding

The `tvmaze_show_id → tmdb_id` bridge exists only to migrate. It is **not** maintained
infrastructure: no scheduled delta job, no monthly re-sweep. Map once, resolve the
residue, verify, cut over, drop the table.

Three tiers, with `match_method` recorded on every row:

1. `/find` by **`tvdb_id`** — 61,999 shows. Exact.
2. `/find` by **`imdb_id`** — picks up 3,791 more. Exact.
3. `/search/tv` by **title + year** — accepted only when *all three* hold: exactly one
   result, normalised-title exact equality, and `first_air_date` year within ±1 of
   `premiered`. No fuzzy scoring, no best-guess. Shows with no premiere date are excluded
   from this tier entirely.

**Fold both sides of a title comparison through Postgres.** The existing folded form is
SQL-side (`immutable_unaccent(lower(...))`, `browse_queries.py:316`) and
`browse_queries.py:468` explicitly warns that a Python-side `unaccent` diverges. TMDB
titles arrive as JSON in Python; pass them in as bind parameters rather than
reimplementing the fold.

### 3. Human matching queue

The residue is small and known: **4 prod shows have no external id**, only one of which has
episode watches. Every show any user has touched must reach a *verified* mapping — an
exact-id match, a reviewed title match, or a locally-authored row.

Episode grain is the real risk: 7,071 records against two sources that disagree about
specials (TMDB parks them in season 0) and season numbering. Map by
`(season_number, episode_number)`; every failure surfaces in the queue rather than being
dropped.

Where TMDB genuinely lacks a show, the fallback is a locally-authored row. Pushing the show
to TMDB upstream is optional and never blocks a user's history.

### 4. Reconciliation is the acceptance test

**Per-user, per-show episode counts must match exactly before and after — 8,499 in, 8,499
out.** A migration that cannot produce that proof does not ship. Same for tracked shows,
ratings and activity events.

## Cutover

**Big-bang with a short announced window.** Build `catalog` fully populated alongside
`tvmaze`, verify, take the app down, repoint `app.*` FKs, bring it up. Dual-running with
feature-flagged reads is the textbook answer and the wrong one for 5 users and 8,499 rows
— the migration itself is seconds of SQL.

**Pre-cutover go/no-go:** a catalog comparison over the populated `catalog` schema
confirming every one of the 88,971 TV Maze shows is either present in TMDB or deliberately
carried as a locally-authored row. This catches a long-tail regression *before* the window.
It is a safety check, not a decision gate — the decision is made.

**Nothing is deleted at cutover.** `DROP SCHEMA tvmaze` is a separate, later ticket,
explicitly gated on the user's approval, leaving the archive and the intact TV Maze mirror
as two independent recovery paths through the risk window.

## Coverage: capture the whole surface, not TV Maze parity

**The default is to capture everything TMDB returns.** With TV Maze, more data meant more
*requests* — AKAs, show cast, show crew and per-season guest cast were each their own
endpoint, so every extra field was a separate multi-hour pass. That is why this repo
accumulated four separate backfills. `append_to_response` rides everything on the same
call, so the marginal cost of a field here is **a column, not a pass**.

The coverage audit therefore runs **TMDB inward**, not TV Maze outward. Auditing "does every
`tvmaze/models.py` column have a home?" guarantees parity with the source we are leaving and
is exactly the shape that produces backfills. Every field in the series, season, episode,
person and `append_to_response` inventories is classified **modeled now / deliberately
skipped / deferred**, each with a reason.

High-value fields with no TV Maze ancestor, each of which maps to a project already filed:

| Field | Would become a backfill for |
|---|---|
| `next_episode_to_air` | Push Notifications, Upcoming |
| `episode_type` (`premiere`/`mid_season`/`finale`/`standard`) | Push Notifications — finale detection with no heuristic |
| `original_name`, `translations` | **TVBF: Localization** — that project *is* this data |
| `content_ratings` | Age ratings; no TV Maze equivalent |
| `watch/providers` | The capability that justifies TMDB beyond coverage |
| `keywords` | Discovery / Personalized Recommendations |
| `created_by` | Show creators — a credit type TV Maze never had |
| `backdrop_path`, `images` | Public Profiles & Sharing |
| `number_of_episodes` / `number_of_seasons` | Stats / Year in Review |
| `episode_groups` | Absolute and DVD orderings — anime, long-running shows |
| Person `gender`, `known_for_department`, `popularity` | Person pages |

### Watch providers carry a separate attribution requirement

Resolved 2026-08-09. Provider data is *"powered by our partnership with JustWatch"*, and the
endpoint docs state: *"In order to use this data you must attribute the source of the data as
**JustWatch**. If we find any usage not complying with these terms we will revoke access to
the API."*

Asked whether a sitewide footer suffices, TMDB staff answered: *"For this data, we expect a
reference or logo on **each media item**, just like we do here on TMDb."* And asked whether
attribution applies when only showing provider icons without deep links: *"Yes, you still
need to. If you're using the data, then you need to attribute them (and us)."*

**The footer-only decision made for TMDB attribution does not extend to watch providers.**
Attribution is to JustWatch *in addition to* TMDB, placed per item.

The obligation attaches to **display, not capture** — storing the data carries no burden, and
nothing in either project surfaces it yet. Recorded here so a future UI project inherits the
constraint rather than discovering it. Non-compliance is explicitly grounds for revoking API
access, which would take the whole catalog down with it.

**The 20-item `append_to_response` cap is shared between namespaces and `season/N` entries.**
Eight namespaces plus twelve seasons is the whole budget, so long-running shows need
follow-up requests. That must be designed into the fetch plan, and the real cap measured
rather than assumed.

> **Measured, NEU-1028 / NEU-1034.** The cap is 20 and 21 is a hard 400. The audit took
> **eleven** namespaces rather than eight, leaving nine season slots — and since a show's
> season numbers are unknowable before the first request, the ingest guesses `season/0..8`
> and reconciles against `seasons[]`. Both halves of that guess are measured: an absent
> `season/N` is dropped from the response silently, and `0..8` covers 97.5% of sampled
> series against 94.0% for `1..9`.

Raw payload storage was considered as insurance and **rejected**: a full re-fetch is cheap
enough relative to the several GB of JSONB it would cost. The TV Maze backfill pain came from
12–29 hour passes per axis, and that problem is gone.

> **Measured, NEU-1034: the re-fetch is ~8.7 hours, not the ~3.2 first estimated here.**
> 7.27 shows/sec over a 150-show sample spread through the export, for ~229k series. The
> budget is not the constraint — the loop is sequential, so latency binds at ~7.6 req/s
> against a 20 req/s allowance. This is the same correction NEU-1065 had to make to the
> enrichment pass, and the general lesson is that any estimate here derived from the request
> budget will be wrong for as long as the passes are sequential. The rejection stands: 8.7
> hours is still a re-fetch that can simply be run again, and it is well inside the 12–29
> hour range that made TV Maze's backfills painful.

### Known losses

| TV Maze | TMDB | Resolution |
|---|---|---|
| `schedule` (day/time) | none | Lost. No weekly-schedule concept upstream. |
| `network` / `web_channel` split | merged `networks` + `watch/providers` | Browse filters need reshaping. |
| Global character ids | free text on credit | Interned per show. |
| `show_aka` | `alternative_titles` | Direct equivalent; AKA search survives. |

### Decisions the audit must make, not enumerate

Status vocabulary (TMDB's five values against our four, read by the SPA's `filterTypes.ts`);
specials representation (TMDB season 0 vs. our null episode number); the **three** language
concepts TMDB carries where TV Maze had one; and what a single "runtime" means given
`episode_run_time` is an array.

## Out of scope

Discovery surfaces — similar shows, trending, most anticipated — belong to
**TVBF: TMDB Discovery**, which is blocked on this project. Personalised recommendations
derived from our own watch data remain in **TVBF: Personalized Recommendations**.

## Milestones

1. **Foundation** — `catalog` schema, TMDB client, generalised request budget with block
   leasing, config, attribution.
2. **User-data safety net** — the archive, the reconciliation harness, the acceptance test.
   Precedes all catalog work.
3. **Catalog ingest** — shows, seasons, episodes, alternative titles; full pass, delta,
   tombstones.
4. **Credits** — cast, crew, guest cast, per-show character interning.
5. **Migration & cutover** — mapping, human queue, repoint, go/no-go, cutover. Deletion of
   `tvmaze` is deliberately excluded and filed separately.
